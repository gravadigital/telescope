# S-002: Propagar y mostrar errores reales en pantallas de gestión y listado

**Status:** Completed
**Created:** 2026-09-21
**Source:** REQ-001

## Historia de Usuario

**Como** organizador o participante de un evento,
**quiero** que la aplicación distinga claramente un fallo de red de un estado real "vacío"
o "no configurado" en las pantallas de gestión y listado,
**para** no tomar decisiones (como avanzar de etapa) sobre datos incompletos o inventados
sin saberlo.

## Criterios de Aceptación

### CA-1: Fallo al cargar participantes en ManageEventPage es distinguible de "sin participantes"

**DADO** un organizador está en la pantalla de gestión de su evento (`ManageEventPage`)
**CUANDO** la carga de participantes falla por un error de red o del servidor
**ENTONCES** ve un mensaje de error distinguible de "no hay participantes", y no ve la
lista vacía como si fuera un hecho real del evento.

### CA-2: Fallo al cargar propuestas (attachments) es visible

**DADO** un organizador está en la pantalla de gestión de su evento
**CUANDO** la carga de propuestas (attachments) falla
**ENTONCES** ve un error visible, y los contadores de propuestas enviadas y el estado por
participante no se muestran como si todos estuvieran pendientes por un hecho real.

### CA-3: Fallo al cargar estadísticas de votación es distinguible de "no configurada"

**DADO** un organizador está en la pantalla de gestión de un evento en etapa de votación o
de resultados
**CUANDO** la carga de estadísticas de votación falla
**ENTONCES** ve un error visible, distinguible de "la votación aún no fue configurada".

### CA-4: Participants.tsx no rellena con datos inventados ante un fallo

**DADO** cualquier usuario abre el componente que lista participantes de un evento
**CUANDO** la carga de participantes falla
**ENTONCES** ve el mensaje de error y la lista de participantes queda vacía o no se
modifica — nunca se rellena con nombres fabricados.

### CA-5: Avance de etapa bloqueado si no se pudo verificar participantes

**DADO** un organizador avanza de etapa o cancela un evento desde `ManageEventPage`
**CUANDO** la carga de participantes falló silenciosamente antes de esa acción
**ENTONCES** el organizador no puede tomar esa decisión sobre datos fabricados o vacíos por
error — la pantalla ya le mostró que la carga falló antes de permitir la acción.

### Flujo de Interacción

#### Escenario: `ManageEventPage` — participantes, adjuntos y estadísticas de votación (CA-1, CA-2, CA-3, CA-5)

**Trigger:** Organizador abre `/events/:eventId/manage`, o el fetch de alguno de los tres
falla tras cargar el evento

**Flujo:**

1. **[web — ManageEventPage.loadEventData]**
   - Acción: Ya carga el evento (`getEventById`) antes de estos tres fetches — sin cambios
     ahí. Depende de que S-001 ya haya hecho que `getEventById` relance errores reales.
   - **Participantes** (líneas 73-79 actuales): en vez de `catch { setParticipants([]) }`,
     se agrega estado `participantsError: string` y se hace `setParticipantsError(...)`.
   - Output: El render (sección "Registered Participants", líneas 534-601) distingue "0
     participantes reales" (mostrar el `empty-state` actual) de "no se pudo cargar"
     (mostrar mensaje de error con opción de reintentar).

2. **[web — ManageEventPage.loadEventData]**
   - **Adjuntos** (líneas 82-88 actuales): mismo patrón — `attachmentsError: string` en vez
     de swallow silencioso a `[]`.
   - Output: El contador "Files Submitted" (línea 401-405) no se muestra como `0 / N` real
     si la carga falló; se muestra el error.

3. **[web — ManageEventPage.loadEventData]**
   - **Estadísticas de votación** (líneas 92-112 actuales): mismo patrón —
     `votingStatsError: string`.
   - Output: La sección "Voting Configuration" (líneas 508-532) no interpreta el fallo como
     "votación no configurada": muestra el error.

4. **[web — ManageEventPage.validateStageAdvance]**
   - Acción: Hoy usa `participants.length` (líneas 226-227, 236-239) para decidir si se
     puede avanzar de etapa. Se agrega chequeo de `participantsError`.
   - Output: Si `participantsError` está seteado, `validateStageAdvance` (o
     `handleAdvanceStageClick`, que la invoca indirectamente vía `getNextStage`) rechaza el
     avance de etapa con un mensaje explícito ("No se puede avanzar: no se pudo verificar
     la lista de participantes. Reintentá antes de continuar.").

**Outcome:** Un fallo de red al cargar cualquiera de los tres recursos se ve como error
visible y bloquea decisiones que dependan de esos datos (avance de etapa), en vez de
mostrarse como un estado vacío/no-configurado que habilita seguir operando sobre datos
incompletos.

**Manejo de errores:**
- Fallo en participantes/adjuntos/stats → estado de error dedicado por recurso, visible en
  la sección correspondiente, con acción de reintento (recargar `loadEventData` o el fetch
  puntual).
- Avance de etapa bloqueado mientras `participantsError` esté activo.

#### Escenario: `Participants.tsx` — componente de listado (CA-4)

**Trigger:** Cualquier usuario abre el modal de participantes desde `EventDetailPage`

**Flujo:**

1. **[web — Participants.fetchParticipants]**
   - Acción: Se elimina el bloque de `mockParticipants` (líneas 28-55 actuales).
   - Output: El `catch` queda solo con `setError('Error loading participants')` (línea 26,
     ya existe) y no llama a `setParticipants(...)` con datos fabricados.
   - El render ya tiene un bloque `{error && !loading && (...)}` (líneas 104-111) con botón
     de reintento — no requiere cambios de render, ya estaba preparado para este caso; solo
     dejaba de usarse porque el `catch` pisaba el estado de error con datos falsos
     inmediatamente después.

**Outcome:** Ante un fallo, el modal muestra el mensaje de error y el botón "🔄 Retry" que
ya existe, en vez de una lista de 3 personas inventadas (María González, Carlos Rodríguez,
Ana López).

**Manejo de errores:**
- Fallo de red/servidor → estado de error visible, `participants` permanece en `[]` (su
  valor inicial, sin modificar).

### Consideraciones Técnicas

**Seguridad:**
- No aplica. No cambia autenticación, autorización, ni el manejo del JWT.

**Performance:**
- No aplica. No se agregan requests adicionales ni se cambia la frecuencia de polling.

**Dependencias:**
- Depende de S-001: `ManageEventPage.loadEventData` necesita que `getEventById` (y las
  llamadas asociadas) relancen errores reales en vez de fallback silencioso para que estos
  tres estados de error dedicados tengan sentido.
- `getEventParticipants` (capa de servicio) **sí** se modifica (decisión tomada al
  planificar): su `catch { return [] }` impedía que los `try/catch` de `ManageEventPage` y
  `Participants` se ejecutaran. Ahora relanza el error; una lista vacía real sigue
  devolviendo `[]`.
- Riesgo de duplicar lógica de render entre los tres estados de error nuevos de
  `ManageEventPage` (`participantsError`, `attachmentsError`, `votingStatsError`).
  Mitigación: complejidad baja, siguiendo el mismo patrón que `downloadError` (línea 22, ya
  existente en el mismo archivo) — es el patrón establecido en el propio componente, no se
  introduce uno nuevo.
