# S-010: Fundaciones del front: tokens, componentes y dominio

**Status:** Ready
**Created:** 2026-10-02
**Source:** REQ-003

## Historia de Usuario

**Como** equipo de desarrollo del front,
**quiero** una única fuente de tokens, una librería de componentes del Design System, un módulo
con las reglas de dominio y errores con `code`,
**para** que cada pantalla del rediseño se arme con piezas comunes, sin duplicar estilos ni reglas,
y sin mostrar textos técnicos al usuario.

## Criterios de Aceptación

### CA-1: Una sola definición de tokens

**DADO** el código del front
**CUANDO** se buscan definiciones de variables CSS de diseño
**ENTONCES** los tokens del DS `web` v2.0.0 (referencia, semánticos y de componente) se definen
solo en `src/styles/tokens.css`; la copia de `index.css` se elimina y las variables viejas que
siguen usando las pantallas actuales quedan en un único bloque marcado como *legacy* en
`styles/global.css`

### CA-2: Componentes sin colores literales

**DADO** cualquier componente de `src/components/ui/`
**CUANDO** se revisa su CSS
**ENTONCES** no contiene hex, `rgb()` ni medidas sueltas que tengan token; todo sale de
`tokens.css`

### CA-3: Librería de primitivos del Design System

**DADO** los componentes del DS `web` v2.0.0
**CUANDO** se revisa `src/components/ui/`
**ENTONCES** existen `Button`, `TextField` (variantes simple, multilínea con contador y búsqueda),
`Dialog`, `DataTable`, `FilterTabs`, `StatusPill`, `StatTile`, `Callout` (info, warning, error,
success, con reintento opcional), `EmptyState`, `Card` (incluye la variante destacada para
franjas CTA), `ProgressBar`, `NumberStepper`, `DateQuickPicker`, `FileDropzone` (con el archivo
elegido) y `Menu`, cada uno según su spec en `docs/design-system/web/components/`

### CA-4: Los componentes no traen texto propio

**DADO** cualquier componente de `src/components/ui/` y de los compuestos de esta story
**CUANDO** se revisa
**ENTONCES** todo texto visible y todo `aria-label` llega por props (los aporta la pantalla desde
el catálogo de S-011); el componente no tiene strings embebidos

### CA-5: Diálogo accesible

**DADO** un `Dialog` abierto
**CUANDO** el usuario navega con teclado
**ENTONCES** tiene `role="dialog"` y `aria-modal="true"`, el foco queda atrapado dentro, Escape lo
cierra y al cerrarse el foco vuelve al elemento que lo abrió. Admite eyebrow de transición
("Creación → Participación"), título, cuerpo y acciones

### CA-6: Tabla apilada en mobile

**DADO** un `DataTable` con columnas y una acción por fila
**CUANDO** se ve a 375 px
**ENTONCES** cada fila se apila mostrando cada valor con la etiqueta de su columna, sin scroll
horizontal

### CA-7: Selector numérico con límites

**DADO** un `NumberStepper` con mínimo 1, máximo 2 y recomendado 2
**CUANDO** el usuario intenta pasar del máximo
**ENTONCES** el botón + queda deshabilitado y se muestra el máximo; el recomendado se marca

### CA-8: Fecha con atajos

**DADO** un `DateQuickPicker` con fecha mínima
**CUANDO** el usuario elige "1 semana"
**ENTONCES** la fecha queda en hoy + 7 días; no se puede elegir una fecha anterior a la mínima

### CA-9: Compuestos de evento reutilizables

**DADO** los patrones de evento presentes en varias pantallas
**CUANDO** se revisa `src/components/events/`
**ENTONCES** existen `EventHero` (banda oscura con volver, chips, título, meta y acciones),
`StageTimeline` (4 etapas con completada / ahora / pendiente, subtítulo y fecha editable
opcional), `NextStepCard` (título, explicación, checklist opcional, aviso de consecuencias, CTA
principal y secundaria) y `ProgressChecklist`, presentacionales y armados con los primitivos

### CA-10: Reglas de dominio en un solo lugar

**DADO** el código del front
**CUANDO** se buscan las reglas de dominio
**ENTONCES** viven en `src/domain/`:
- `stages.ts`: orden de etapas, siguiente etapa, clave de nombre de cada etapa y reglas de avance
  que se validan en el cliente
- `files.ts`: tipos permitidos (JPG, PNG, GIF, WebP, PDF, TXT, DOC, DOCX) y límite de 10 MB,
  iguales a los del backend
- `dates.ts`: formateo de fechas, fechas relativas y "días al cierre" con `Intl`, recibiendo el
  idioma; fechas sin hora se interpretan como fin del día
- `score.ts`: puntaje `mbc_score × 10` con un decimal y separador según idioma
- `voting.ts`: validación de umbrales (`good > bad` y diferencia ≥ 0,1) y
  `min_evaluations_per_file` recomendado = `min(3, m)`, con referencia a
  `GET …/voting-config/preview` (el `m` recomendado y el máximo no se recalculan en el cliente)

### CA-11: Errores con código

**DADO** una respuesta de error de la api
**CUANDO** `apiRequest` la procesa
**ENTONCES** lanza `ApiError { status, code, message, details }`; para la forma B de los
middlewares (`{ error: "UNAUTHORIZED", message }`), `code = body.code ?? body.error`. `ApiError`
extiende `Error`, así las pantallas actuales siguen funcionando hasta que se reemplacen

### CA-12: Código muerto eliminado

**DADO** el código del front
**CUANDO** se aplica esta story
**ENTONCES** ya no existen `ApiStatusAuth`, `Voting` ni `components/event-detail/EventDetail` (si
existe), y no queda ninguna importación rota

### CA-13: Tests de las fundaciones

**DADO** la suite de tests del front
**CUANDO** se ejecuta
**ENTONCES** hay tests unitarios de cada módulo de `src/domain/`, de `ApiError` y de los
comportamientos interactivos de `Dialog`, `DataTable`, `NumberStepper`, `DateQuickPicker` y
`FileDropzone`, y la suite completa pasa

## Diseño Técnico

### Servicios Afectados

| Servicio | Impacto | Cambios Necesarios | Estado |
|----------|---------|-------------------|--------|
| `web` | Alto | `src/styles/tokens.css`; `src/components/ui/` (15 componentes del DS); compuestos de evento; `src/domain/`; `ApiError` en `config/api.ts`; borrado de código muerto | Pending |

### Decisiones de arquitectura

- **DA-7 (enmienda a ADR-007):** se mantiene CSS plano por componente y tokens en `:root`, pero con
  una sola fuente (`src/styles/tokens.css`), sin hex literales en componentes nuevos y con el
  lenguaje visual "bandas oscuras + contenido claro" del DS v2.0.0. Breakpoints como escala
  nombrada (`--bp-mobile: 768px` documentado; en `@media` se usa el literal). **Mobile-first** en
  los componentes nuevos. Prefijo de clase por componente para evitar colisiones.
- **DA-8:** una carpeta por componente con su CSS.
  - `src/components/ui/{kebab}/` — primitivos sin dominio.
  - `src/components/{dominio}/` — compuestos con dominio.
  - `Dialog` reemplaza a las tres implementaciones de overlay (`Modal`, `stage-modal-*`,
    `share-menu`). Las viejas se borran en la story que reemplaza la pantalla que las usa.
- **DA-5:** reglas de dominio del front en `src/domain/`, sin duplicar las del backend.
- **DA-6:** `ApiError` conserva `code`; la web traduce por `code` (el catálogo `errors.*` lo
  completa S-011).

### Flujo de Interacción

#### Escenario: Error de la api mostrado al usuario (CA-11)

1. **[web — `apiRequest`]** recibe `409 { error, code: "INVALID_UPDATE_STAGE", current_stage }`.
2. **[web]** lanza `ApiError { status: 409, code: "INVALID_UPDATE_STAGE", message, details }`.
3. **[web — pantalla]** muestra `t('errors.INVALID_UPDATE_STAGE')` con fallback genérico (S-011);
   nunca `err.message`.

### Flujos Afectados

Ninguno a nivel de sistema (los cambios de los pasos de la web en cada flujo los aplican las
stories de pantalla).

### Consideraciones Técnicas

**Accesibilidad:**
- `Dialog` con foco atrapado, Escape y retorno del foco. `Callout` de error con `role="alert"`.
- `NumberStepper` y `DateQuickPicker` operables con teclado.

**Responsive:**
- Mobile-first en todos los componentes nuevos; verificación a 375 px.

**Riesgos:**
- Conviven el lenguaje visual viejo y el nuevo hasta que se reemplacen todas las pantallas. Se
  acota con el bloque *legacy* de `global.css`, que se borra en la última story de pantalla.
- Esta story no cambia pantallas: los componentes se prueban con tests y se usan desde S-011 en
  adelante.

**Dependencias:**
- Ninguna previa. Usa el DS `web` v2.0.0 ya documentado.
