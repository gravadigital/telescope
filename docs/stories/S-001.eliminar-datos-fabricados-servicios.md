# S-001: Eliminar datos fabricados de la capa de servicios (api.ts)

**Status:** Completed
**Created:** 2026-09-21
**Source:** REQ-001

## Historia de Usuario

**Como** usuario de la aplicación (organizador o participante),
**quiero** que la capa de servicios nunca me muestre datos inventados ni me loguee con una
sesión fabricada cuando la API falla,
**para** poder confiar en que lo que veo en pantalla refleja el estado real del sistema, o
un error visible si no pudo obtenerse.

## Criterios de Aceptación

### CA-1: Login con validación vacía muestra el error real

**DADO** un usuario completó el formulario de login con el email vacío
**CUANDO** envía el formulario
**ENTONCES** ve el mensaje de error de validación real ("Email is required") y no queda
logueado.

### CA-2: Login con fallo real de API no loguea con token demo

**DADO** un usuario completa el formulario de login correctamente pero la API de
autenticación falla por un motivo real (no de validación)
**CUANDO** envía el formulario
**ENTONCES** ve un mensaje de error real y no queda logueado con un token demo fabricado
(`demo-token-{timestamp}`).

### CA-3: Health check de la API de login refleja el estado real

**DADO** cualquier usuario en la pantalla de login
**CUANDO** la API de autenticación no está disponible
**ENTONCES** el indicador de salud de la API refleja esa caída real, en vez de mostrar
siempre disponible.

### CA-4: Listado de eventos no fabrica eventos ante un fallo

**DADO** cualquier pantalla que liste eventos
**CUANDO** la carga del listado de eventos falla por un error de red o del servidor
**ENTONCES** la pantalla muestra un estado de error real, y nunca aparecen eventos
fabricados con datos de votos o propuestas inventados.

### CA-5: Detalle de evento no fabrica un evento ante un fallo

**DADO** un usuario navega al detalle de un evento específico
**CUANDO** la carga de ese evento falla por un error de red o del servidor
**ENTONCES** ve un estado de error real, y nunca se le muestra un evento fabricado, aunque
el identificador solicitado coincida con uno de los valores usados internamente como
fallback.

### CA-6: Eventos del usuario autenticado distinguen "sin eventos" de "fallo al cargar"

**DADO** un usuario autenticado
**CUANDO** la carga de los eventos en los que participa falla por un error de red o del
servidor
**ENTONCES** el sistema distingue "el usuario no está registrado en ningún evento" de "no
se pudo cargar la información", y no oculta el fallo como una lista vacía silenciosa.

### Flujo de Interacción

#### Escenario: Login con fallo de validación o de API (CA-1, CA-2)

**Trigger:** Usuario envía el formulario de login/registro en `AuthForm`

**Flujo:**

1. **[web — AuthForm.tsx]**
   - Acción: Valida `email` y `password` **antes** del `try` que envuelve la llamada a la
     API (o en un `try/catch` propio que no comparte alcance con el de la API).
   - Output: Si falta un campo → `setError("Email is required")` (o el mensaje
     correspondiente) y retorna. No se ejecuta ninguna llamada a `UserService`.

2. **[web — AuthForm.tsx, validación pasada]**
   - Acción: `UserService.authenticateUser(email, password)` → `POST
     /api/v1/users/authenticate`
   - Output: Si la API responde error real (credenciales inválidas, servidor caído, red
     caída), `apiRequest` lanza `Error`, el `catch` interno ya existente (líneas 103-128 de
     `AuthForm.tsx`) lo captura y hace `setError(errorMessage)`.

**Outcome:** Error de validación o de API real se muestra como mensaje de error; el usuario
nunca queda logueado con una sesión fabricada.

**Manejo de errores:**
- Validación vacía → mensaje de validación real, sin llamar a la API.
- API falla (red, servidor, credenciales) → mensaje de error real, sin login.
- Se elimina el `catch` externo que fabrica `demo-token-{timestamp}` (líneas 132-152
  actuales de `AuthForm.tsx`). No hay login con token fabricado bajo ninguna circunstancia.

---

#### Escenario: Indicador de salud de la API en el login (CA-3)

**Trigger:** Se monta el componente `Auth`

**Flujo:**

1. **[web — Auth.tsx]**
   - Acción: `ApiHealthService.checkHealth()` → internamente `GET /health` (ya implementado
     en `config/api.ts:196-204`, sin cambios ahí).
   - Output: `setApiAvailable(isHealthy)` con el resultado real, no `true` hardcodeado
     (reemplaza la línea 31-37 actual de `Auth.tsx`).

**Outcome:** El texto "API is not available, running in local mode" (línea 151 de
`Auth.tsx`) refleja una caída real. Dado que el modo demo se elimina (escenario anterior),
este mensaje pasa a ser puramente informativo — no habilita ningún fallback. Se mantiene
porque comunica al usuario por qué el login podría fallar.

**Manejo de errores:**
- Si `/health` no responde o responde `503` → `checkApiHealth()` ya devuelve `false`
  (`config/api.ts:200-203`, `catch` existente). No requiere cambios en `config/api.ts`.

---

#### Escenario: Carga de eventos y detalle de evento (CA-4, CA-5, CA-6)

**Trigger:** Usuario navega a `/events`, a `/events/:eventId`, o se restaura su sesión

**Flujo:**

1. **[web — EventService.getAllEvents]**
   - Acción: `GET /api/v1/events?limit=100`
   - Output: Si `apiRequest` lanza (red caída, servidor caído, respuesta inválida), se
     elimina el fallback de 2 eventos fabricados (líneas 83-111 actuales). El método
     relanza el error (`throw error` en vez de `return [...]`).
   - → `Events.tsx` (`checkApiAndFetchEvents`, ya tiene `try/catch` con `setError`, líneas
     38-56) recibe el error y lo muestra. No requiere cambios en `Events.tsx`: ya propaga
     correctamente, el problema estaba 100% en el servicio.

2. **[web — EventService.getEventById]**
   - Acción: `GET /api/v1/events/:id`
   - Output: Si `apiRequest` lanza, se elimina el fallback que busca en `getAllEvents()`
     (líneas 213-225 actuales). El método relanza el error en vez de devolver `null`
     silenciosamente tras el intento de fallback.
   - Nota: hoy el método ya devuelve `null` como "no encontrado" para el caso de respuesta
     vacía (línea 183-185) — ese camino no cambia, sigue siendo el contrato correcto para
     "no existe". Lo que cambia es que un error de red/servidor real ya no cae en el mismo
     `null` disfrazado de fallback silencioso: se relanza como error para que el caller lo
     distinga.
   - → `EventDetailPage.fetchEventDetails` (línea 91, `catch` existente) y
     `ManageEventPage.loadEventData` (línea 117, `catch` existente) ya diferencian error vs
     `null` en su lógica. No requieren cambios, salvo que ahora sí van a recibir el error
     real en vez de nunca verlo.

3. **[web — UserService.getUserEvents, invocado por AuthContext.syncUserEvents]**
   - Acción: `GET /api/v1/users/:userId/events`
   - Output: Si `apiRequest` lanza, se elimina el `return []` del catch (línea 535 actual).
     Se relanza el error.
   - → `syncUserEvents` (líneas 60-78 de `AuthContext.tsx`) ya tiene su propio `try/catch`
     que hoy solo loguea (`console.error`, línea 76) sin tocar estado. Este comportamiento
     se mantiene sin cambios (ver Consideraciones Técnicas del REQ-001 original: es
     aceptable para una sincronización en background, fuera del alcance de esta story).

**Outcome:** Ningún error de red/servidor se disfraza de "lista vacía" ni de "evento
inventado". Las pantallas que ya tenían manejo de error correcto (todas, salvo
`Participants.tsx`, cubierto en S-002) empiezan a recibirlo de verdad.

**Manejo de errores:**
- Fallo real de red/servidor en cualquiera de los tres métodos → se relanza como `Error`,
  cae en el `catch` ya existente de cada caller.
- Respuesta 200 con lista vacía real → sigue siendo lista vacía real (comportamiento
  correcto, no se toca).

### Consideraciones Técnicas

**Seguridad:**
- No aplica. No cambia autenticación, autorización, ni el manejo del JWT. El 401 global
  (ADR-008, `CustomEvent auth:logout`) no se toca.

**Performance:**
- No aplica. No se agregan requests adicionales ni se cambia la frecuencia de polling.

**Dependencias:**
- Ninguna dependencia externa. `getEventParticipants` (usado en S-002) **no** se modifica
  en esta story: hoy ya hace `catch { return [] }` sin datos fabricados a nivel de
  servicio — el problema de datos fabricados en participantes está en el componente
  `Participants.tsx`, cubierto en S-002.
- Riesgo: al eliminar `getAllEvents()` como fallback de `getEventById()`, cualquier código
  que dependiera implícitamente de ese camino (por ejemplo, ids de eventos demo
  hardcodeados: `68a94135-...`, `660e8400-...`) deja de funcionar. Mitigación: se confirmó
  por lectura de `EventDetailPage.tsx` y `ManageEventPage.tsx` que ambos ya manejan `null` y
  error como casos separados y correctos; ninguno depende del fallback. Verificar en QA que
  no queden otras referencias a esos dos ids fuera de `api.ts`.
