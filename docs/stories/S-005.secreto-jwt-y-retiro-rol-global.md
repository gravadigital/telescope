# S-005: Secreto JWT obligatorio y retiro del rol global

**Status:** Ready
**Created:** 2026-09-25
**Source:** REQ-002

## Historia de Usuario

**Como** responsable de la operación de la plataforma,
**quiero** que la API no arranque sin un `JWT_SECRET` explícito y que ningún permiso dependa
de un rol global de usuario,
**para** que nadie pueda firmar tokens con un secreto conocido y que el acceso a cada evento
salga únicamente de la Participación (`creator` / `participant`).

## Criterios de Aceptación

### CA-1: Arranque con secreto explícito

**DADO** que `JWT_SECRET` está definida con un valor explícito
**CUANDO** se inicia el servicio de API
**ENTONCES** arranca normalmente y firma los tokens con ese secreto

### CA-2: Arranque sin secreto

**DADO** que `JWT_SECRET` no está definida, o está definida vacía
**CUANDO** se inicia el servicio de API
**ENTONCES** el servicio no arranca, registra `JWT_SECRET is required` y sale con código ≠ 0,
antes de conectarse a la base, sin imprimir valores de otras variables

### CA-3: El CLI de migraciones no exige el secreto

**DADO** que `JWT_SECRET` no está definida
**CUANDO** se ejecuta `cmd/migrate`
**ENTONCES** las migraciones corren normalmente

### CA-4: El stack local sigue arrancando sin configurar nada

**DADO** un clon limpio del repo
**CUANDO** se levanta con `deploy/docker-compose.yml` o con el `Makefile`
**ENTONCES** la API arranca, porque ambos ya definen un `JWT_SECRET` de desarrollo

### CA-5: El creador gestiona su evento sin rol global

**DADO** que se retiró `users.role`
**CUANDO** Ana, como `creator`, pausa, cancela, avanza la etapa, cambia la fecha estimada,
configura la votación o genera las asignaciones de su evento
**ENTONCES** todo sigue funcionando: sus permisos salen solo de su Participación `creator`

### CA-6: Un ex-`admin` no gestiona eventos ajenos

**DADO** que Elena tenía `users.role = admin` antes del retiro y no es `creator` de
"Becas 2026"
**CUANDO** intenta pausar, avanzar la etapa o configurar la votación de "Becas 2026"
**ENTONCES** recibe `403 FORBIDDEN` con el mensaje "Only the event creator can perform this
action"

### CA-7: Un ex-`organizer` no configura la votación de eventos ajenos

**DADO** que un usuario tenía `users.role = organizer` y no es `creator` de "Becas 2026"
**CUANDO** intenta `POST .../voting-config` o `POST .../generate-assignments`
**ENTONCES** recibe `403 FORBIDDEN`

### CA-8: Un ex-`admin` no accede a propuestas, datos ni asignaciones ajenas

**DADO** que Elena tenía `users.role = admin`, y no es dueña, ni `creator`, ni tiene asignada
la propuesta de Carla
**CUANDO** intenta descargar la propuesta de Carla, consultar los datos de Carla, o leer la
asignación, el ranking o el borrador de otro participante
**ENTONCES** recibe `403 FORBIDDEN`

### CA-9: Registro sin rol global

**DADO** que se retiró el rol global
**CUANDO** un visitante se registra (con email o con Google) o se registra a un evento por link
**ENTONCES** el usuario se crea sin rol global y sus permisos dependen solo de sus
Participaciones

### CA-10: Las respuestas de usuario ya no incluyen `role`

**DADO** que se retiró el rol global
**CUANDO** se llama a `POST /api/v1/users`, `POST /api/v1/users/authenticate` o
`GET /api/v1/users/{user_id}`
**ENTONCES** el objeto `user` trae `id`, `name`, `lastname`, `email`, `created_at` y no trae
`role`; y el token emitido no lleva el claim `role`

### CA-11: Los tokens previos siguen siendo válidos

**DADO** un token emitido antes del despliegue, con el claim `role`
**CUANDO** se usa contra la API nueva
**ENTONCES** se acepta (el claim sobrante se ignora) y no hace falta volver a iniciar sesión

### CA-12: El frontend no depende del rol global

**DADO** que se retiró el rol global
**CUANDO** un usuario usa la aplicación web
**ENTONCES** `isOrganizer` en el detalle del evento es verdadero solo para el creador, y el
modal de participantes ya no muestra el badge de rol (`Participante` / `Organizador` /
`Administrador`)

### CA-13: Una sesión guardada con `role` no rompe

**DADO** que el navegador tiene en `localStorage` (`telescopio_user`) una sesión guardada con
el campo `role`
**CUANDO** se abre la aplicación después del despliegue
**ENTONCES** la sesión se restaura y el campo sobrante se ignora

## Diseño Técnico

### Servicios Afectados

| Servicio | Impacto | Cambios Necesarios | Estado |
|----------|---------|-------------------|--------|
| `api` | Alto | `JWT_SECRET` en `config` con `Validate()` y `auth.SetSecret`; retiro de `users.role`: migración 022, entidad `participant.User`, claims y firma de `GenerateToken`, bypass de `admin`/`organizer` en `permissions.go` y `canDownload`, `role` en respuestas y en registros; tests | Pending |
| `web` | Bajo | Quitar `role` de `User` (`types/index.ts`) y `ApiUser` (`services/api.ts`) y de sus mapeos; `isOrganizer` = solo creador; quitar el badge de rol de `Participants.tsx` y el `role` del mapeo de `getEventParticipants`; actualizar tests | Pending |

### Cambios de API

#### Endpoints Existentes a Modificar

**`UserSummary`** (ref: `docs/apis/api.yaml:1649`) — usado por `POST /api/v1/users` (l. 113),
`POST /api/v1/users/authenticate` (l. 149) y `GET /api/v1/users/{user_id}` (l. 353):
- **Cambio:** se elimina la propiedad `role` (`enum: [admin, organizer, participant]`,
  nullable). Los handlers arman el payload a mano (`user_handler.go:121,194,220`): se quita la
  clave `"role"` en los tres. `POST /api/v1/auth/google/*` no devuelve `role` (sin cambios).
- **Justificación:** RF-6 del REQ; ADR-005 (quitar el campo de la entidad cambia la respuesta).

**Endpoints con autorización por rol global** — sin cambio de contrato, cambia quién pasa:

| Endpoint (ref `api.yaml`) | Middleware hoy | Después |
|---|---|---|
| `PATCH .../{event_id}/stage` (l. 663) | `RequireEventOwner` (autor o `admin`) | `RequireEventOwner` (solo autor) |
| `PATCH .../{event_id}/estimated-end-date` (l. 734) | ídem | ídem |
| `PATCH .../{event_id}/cancel` (l. 790) | ídem | ídem |
| `PATCH .../{event_id}/pause` (l. 829) | ídem | ídem |
| `POST .../{event_id}/voting-config` (l. 1102) | `RequireEventOwnerOrOrganizer` (autor, `organizer` o `admin`) | `RequireEventOwner` |
| `POST .../{event_id}/generate-assignments` (l. 1190) | ídem | `RequireEventOwner` |
| `.../participants/{participant_id}/assignment`, `ranking-votes`, `vote-draft` (l. 1242, 1279, 1342) | `RequireParticipantOrOwner` (propio, autor o `admin`) | propio o autor |
| `GET /api/v1/attachments/{attachment_id}/download` (l. 1034) | `canDownload` con bypass `admin` (`attachment_handler.go:537`) | sin bypass: dueño, autor o evaluador (regla de S-003) |

- Descripciones del spec a corregir: "o un admin" / "un organizador o un admin" (l. 668,
  1107, 1248) y la mención de `admin` en la descarga.
- El mensaje de `403` de `RequireEventOwner` pasa a "Only the event creator can perform this
  action".
- **Justificación:** RF-6 del REQ; corrige NFR-S-03.

#### Cambio de contrato del JWT

- Claims (`auth-jwt`, sección Token): `user_id`, `email`, ~~`role`~~ (eliminado), más los
  registrados.
- `auth.GenerateToken(userID, email)` pierde el parámetro `role` (llamadores:
  `user_handler.go:103,176`, `google_auth_handler.go:93,198`).
- `JWTAuthMiddleware` deja de setear `user_role` (`jwt.go:126`).
- Se eliminan `GetUserRoleFromContext` (`jwt.go:148`), `RequireRole` (sin usos en rutas) y
  `RequireEventOwnerOrOrganizer` (equivale a `RequireEventOwner` sin roles globales).
- Tokens emitidos antes del despliegue siguen siendo válidos: `golang-jwt` ignora el claim
  `role` sobrante al parsear en `Claims`.

#### Configuración

- `JWT_SECRET` pasa a `config` (`config.md`, "Agregar una variable"): campo nuevo
  `cfg.Auth.JWTSecret` (struct anidado `Auth`), cargado en `Load()` **sin default**.
- Método nuevo `(*Config).Validate() error` que exige `JWT_SECRET` no vacío (solo presencia,
  sin chequeo de fortaleza).
- `cmd/api/main.go:24` llama a `Validate()` tras `Load()` y hace
  `log.Fatal("JWT_SECRET is required", ...)` si falla, antes de conectar a la base.
- `auth` recibe el secreto por `auth.SetSecret(cfg.Auth.JWTSecret)`, llamada desde `main.go`
  antes de registrar rutas; se elimina el `init()` de `jwt.go:18-26` (y con él el default
  hardcodeado).
- **Por qué `Validate()` separado y no dentro de `Load()`:** `cmd/migrate/main.go:15` también
  usa `config.Load()` y no firma tokens; exigir el secreto ahí rompería el CLI de migraciones.
- `deploy/docker-compose.yml:97` y `Makefile:26` ya definen un `JWT_SECRET` explícito de
  desarrollo: no requieren cambios.
- **Justificación:** RF-5 del REQ; corrige D-12.

#### Nuevos Endpoints

Ninguno.

### Cambios de Base de Datos

#### Tablas Existentes a Modificar

**`users`** (ref: `docs/db-schemas/telescopio_db.md:188`)
- **Eliminar columna:** `role user_role` (nullable). Los valores se descartan sin preservar
  (decisión de negocio; cierra la pregunta abierta #2 del PRD).
- **Eliminar índice:** `idx_users_role` (migración 003).
- **Eliminar tipo:** enum `user_role` (migración 001). Ninguna vista (migración 005) ni
  trigger (migración 004) lo referencia.
- **Migración:** `022_drop_user_role.go`
  - `Up`: `DROP INDEX IF EXISTS idx_users_role; ALTER TABLE users DROP COLUMN IF EXISTS role;
    DROP TYPE IF EXISTS user_role;`
  - `Down`: `CREATE TYPE user_role AS ENUM ('admin','participant','organizer'); ALTER TABLE
    users ADD COLUMN role user_role; CREATE INDEX idx_users_role ON users(role);` — restaura
    la estructura, **no los valores**.
  - Sin downtime: `DROP COLUMN` en Postgres es un cambio de catálogo.
- **Código que lee la columna y cambia en esta misma story:**
  - `participant.User.Role` (`participant.go:41`), el tipo `Role` y sus constantes, `IsValid`,
    los helpers `NewAdmin`, `NewOrganizer`, `UpdateRole`, `IsAdmin`, `IsOrganizer`, la
    validación de l. 183 y el parámetro `role` de `NewUser`.
  - El `SELECT ... users.role` de `GetEventParticipants` (`user_repository.go:304`).
  - Los registros que asignan `Role: participant.RoleParticipant` (`user_handler.go:77`,
    `google_auth_handler.go:186`, `event_handler.go:739`).
- `migrations/006_sample_data.go` y `migrations/models.go` **quedan como están**: corren
  antes de la 022 en una base nueva y son historia de migraciones.

#### Nuevas Tablas

Ninguna.

### Flujo de Interacción

#### Escenario: arranque del servicio (CA-1 a CA-4)

**Trigger:** se ejecuta el binario de `cmd/api`

**Flujo:**

1. **[api — `main`]** `config.Load()` → `cfg.Validate()`
2. Si `JWT_SECRET` está vacío → log `JWT_SECRET is required` y salida con código ≠ 0
   (antes de conectar a la base)
3. Si está → `auth.SetSecret(cfg.Auth.JWTSecret)` → conexión, migraciones (incluida la 022),
   rutas

**Outcome:** no existe un camino en el que la API firme tokens con un secreto por default.

**Manejo de errores:**
- Secreto ausente o vacío → el proceso termina con un mensaje explícito

#### Escenario: gestión del evento sin rol global (CA-5 a CA-8)

**Trigger:** un usuario autenticado llama a un endpoint de gestión del evento

**Flujo:**

1. **[api — `JWTAuthMiddleware`]** valida el token (con o sin claim `role`); setea `user_id`,
   `user_email`
2. **[api — `RequireEventOwner` / `RequireParticipantOrOwner`]**
   - Antes: `role == admin` (u `organizer`) ⇒ pasa; si no, `event.AuthorID == userID`
   - Después: solo `event.AuthorID == userID` (o, en `RequireParticipantOrOwner`, que el
     `participant_id` sea el propio)
3. En otro caso → `403 FORBIDDEN` (forma `MiddlewareError`)

**Outcome:** los permisos salen únicamente de la Participación.

#### Escenario: registro de usuarios (CA-9, CA-10)

`POST /users`, `/auth/google/register` y `POST /events/{id}/register` crean el usuario sin
`Role`; `GenerateToken(user.ID, user.Email)`; la respuesta no incluye `role`.

#### Escenario: frontend (CA-12, CA-13)

1. **[web — tipos]** se quita `role` de `User` (`types/index.ts:6`) y de `ApiUser`
   (`services/api.ts:32`), y de los mapeos en `services/api.ts:340,385,409,438,783` y
   `components/auth/Auth.tsx:55`.
2. **[web — `EventDetailPage`]** `isOrganizer = isEventCreator` (`EventDetailPage.tsx:251`).
   Los bloques de organizador de la zona de acción quedan inalcanzables (el creador es
   redirigido a S-05); retirar ese código no es alcance de esta story.
3. **[web — `Participants.tsx`]** se eliminan `getRoleDisplayName`, `getRoleIcon` y el
   `<span className="participant-role ...">` (l. 36-53, 108-109), junto con sus estilos si
   quedan sin uso.
4. **[web — tests]** se quita `role` de los fixtures (`ManageEventPage.test.tsx`,
   `Participants.test.tsx`, `AuthForm.test.tsx`, `api.test.ts`).

Una sesión guardada en `localStorage` con `role` se deserializa igual: el campo sobra y no
se lee.

### Consideraciones Técnicas

**Seguridad:**
- Cierra D-12 (secreto por default conocido) y el bypass de NFR-S-03.
- El mensaje de error de `JWT_SECRET` no debe imprimir valores de otras variables.
- Los middlewares de auth no tienen tests (`testing.md`, "Qué falta"): esta story suma tests
  de `RequireEventOwner` y `RequireParticipantOrOwner` sin rama de `admin`, y de
  `Config.Validate()`.

**Performance:**
- Sin impacto: se eliminan ramas de chequeo, no se agregan consultas.

**Dependencias y riesgos:**
- **Migración y código se despliegan juntos.** La 022 corre al arrancar
  (`postgres.AutoMigrate`); un binario viejo contra una base migrada rompe
  `GetEventParticipants` y el `Scan` de `User`. Por eso la migración y el retiro del campo en
  Go van en esta misma story.
- **Tests que setean `user_role`** (`attachment_handler_test.go:410-422` y los casos de
  l. 197-521, incluido el test de bypass `admin` de l. 373, que se reemplaza por uno que
  espera `403`) y los que usan `participant.Role` (`google_auth_handler_test.go:143`,
  `user_handler_test.go:146`) dejan de compilar: se actualizan acá.
- **Tests que firman tokens:** al quitar el `init()`, el secreto queda vacío hasta que
  alguien llame a `SetSecret`; los tests que generen o validen tokens deben setearlo.
- Toca `canDownload` y `permissions.go`, que modifica S-003: se implementa después de S-003.

## Dependencias

**Prerequisitos:**
- S-003: Reglas de acceso a propuestas y a datos de usuario (mismos archivos:
  `permissions.go`, `canDownload`; el `UserSummary` de `GET /users/{user_id}` que restringe
  S-003 pierde `role` acá).

**Habilita:**
- Ninguna story del request depende de esta.

**Externas:**
- Los entornos desplegados (fuera del stack local) deben tener `JWT_SECRET` definido antes
  del despliegue, o la API no arranca.
