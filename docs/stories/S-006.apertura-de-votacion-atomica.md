# S-006: Apertura de votación atómica y reglas de avance

**Status:** Completed
**Created:** 2026-10-02
**Source:** REQ-003

## Historia de Usuario

**Como** organizador de un evento,
**quiero** abrir la votación en un solo paso que avance la etapa, guarde la configuración y genere
las asignaciones solo para quienes subieron propuesta,
**para** no dejar el evento en un estado intermedio irreversible y que nadie sin propuesta evalúe
ni sea evaluado.

## Criterios de Aceptación

### CA-1: Abrir la votación en una sola operación

**DADO** un evento en `participation` con 4 inscriptos y 3 propuestas
**CUANDO** el organizador envía `PATCH /events/{event_id}/stage` con
`{ stage: "voting", estimated_end_date, voting_config: { attachments_per_evaluator: 2 } }`
**ENTONCES** el evento pasa a `voting`, se guarda la configuración con los valores por defecto
para lo que no se envió, se generan asignaciones solo para los 3 participantes con propuesta y la
respuesta incluye `voting: { configuration, assignments_count: 3, total_attachments: 3 }`

### CA-2: Sin propuesta no se evalúa ni se es evaluado

**DADO** el evento de CA-1
**CUANDO** se generan las asignaciones
**ENTONCES** el inscripto sin propuesta no tiene fila en `assignments` y ninguna asignación
contiene una propuesta suya

### CA-3: Mínimo de 3 participantes con propuesta

**DADO** un evento en `participation` con 5 inscriptos y 2 propuestas
**CUANDO** el organizador intenta pasar a `voting`
**ENTONCES** recibe `400 INSUFFICIENT_ATTACHMENTS` con `current_count: 2` y
`required_minimum: 3`, y el evento sigue en `participation`. La regla anterior de 3 inscriptos
(`INSUFFICIENT_PARTICIPANTS`) ya no se aplica

### CA-4: La configuración es obligatoria para abrir la votación

**DADO** un evento en `participation` con 3 o más propuestas
**CUANDO** se envía `PATCH /stage` con `stage: "voting"` sin `voting_config`
**ENTONCES** recibe `400 MISSING_VOTING_CONFIG` y la etapa no cambia

### CA-5: Valor por defecto de evaluaciones mínimas por propuesta

**DADO** un evento con 3 propuestas y `attachments_per_evaluator: 2`, sin
`min_evaluations_per_file`
**CUANDO** se abre la votación
**ENTONCES** se usa `min_evaluations_per_file = min(3, 2) = 2` y la validación de cobertura pasa

### CA-6: Configuración fuera de rango

**DADO** un evento con 3 propuestas
**CUANDO** se envía `attachments_per_evaluator: 3` (mayor a propuestas − 1)
**ENTONCES** recibe `400 M_EXCEEDS_EVALUABLE` y la etapa no cambia

### CA-7: Umbrales de calidad validados en Go

**DADO** un pedido de apertura de votación
**CUANDO** `quality_good_threshold <= quality_bad_threshold` o la diferencia es menor a 0,1
**ENTONCES** recibe `400 INVALID_THRESHOLDS` (no un 500 por el CHECK de la base) y la etapa no
cambia

### CA-8: Rollback si falla la escritura

**DADO** un pedido válido de apertura de votación
**CUANDO** falla la inserción de las asignaciones
**ENTONCES** responde `500 VOTING_SETUP_ERROR`, no queda configuración ni asignaciones guardadas
y el evento sigue en `participation`

### CA-9: Vista previa del reparto

**DADO** un evento propio en `participation` con 4 inscriptos y 3 propuestas
**CUANDO** el organizador pide `GET /events/{event_id}/voting-config/preview`
**ENTONCES** recibe `participants_count: 4`, `participants_with_proposal: 3`,
`can_open_voting: true`, `min_m`, `max_m: 2`, `recommended_m` y los `defaults` de los umbrales,
calculados con la misma lógica que valida la apertura

### CA-10: Vista previa con menos de 3 propuestas

**DADO** un evento con 2 propuestas
**CUANDO** se pide la vista previa
**ENTONCES** `can_open_voting` es `false`

### CA-11: Vista previa solo para el organizador

**DADO** un usuario que no es el autor del evento
**CUANDO** pide la vista previa
**ENTONCES** recibe 403 (middleware `RequireEventOwner`)

### CA-12: Publicar con rankings faltantes guarda el resultado

**DADO** un evento en `voting` con 1 de 4 rankings enviados
**CUANDO** el organizador pasa el evento a `results`
**ENTONCES** el cálculo se persiste en `voting_results` (el CHECK relajado lo permite) y el
ranking queda disponible

### CA-13: WebP aceptado

**DADO** un participante inscripto en `participation`
**CUANDO** sube una propuesta `image/webp` de menos de 10 MB
**ENTONCES** se acepta igual que los demás tipos permitidos

### CA-14: Endpoints viejos con la misma regla

**DADO** los endpoints `POST /voting-config` y `POST /generate-assignments`
**CUANDO** se usan
**ENTONCES** aplican la misma regla (solo participantes con propuesta, mínimo 3 propuestas) y
figuran como `deprecated` en el OpenAPI

## Diseño Técnico

### Servicios Afectados

| Servicio | Impacto | Cambios Necesarios | Estado |
|----------|---------|-------------------|--------|
| `api` | Alto | `UpdateEventStage` con `voting_config` y transacción; evaluadores = participantes con propuesta; mínimo 3 propuestas; default `min(3, m)`; `INVALID_THRESHOLDS` en Go; ruta `GET /voting-config/preview`; migración 023 (CHECK de `voting_results`); `image/webp` | Done |

### Cambios de API

#### Endpoints Existentes a Modificar

**`PATCH /api/v1/events/{event_id}/stage`** (ref: `docs/apis/api.yaml:667`)

Request:
```yaml
stage: Stage
estimated_end_date: string(date)     # obligatoria si stage es participation o voting
voting_config:                       # NUEVO — obligatorio si stage = voting
  attachments_per_evaluator: integer   # req, 1..50
  quality_good_threshold: number       # opt, default 0.6
  quality_bad_threshold: number        # opt, default 0.3
  adjustment_magnitude: integer        # opt, 1..10, default 3
  min_evaluations_per_file: integer    # opt, 1..20, default min(3, attachments_per_evaluator)
```

Response `{data, message, code: STAGE_UPDATED, transition}` y, cuando `stage = voting`:
```yaml
voting:
  configuration: VotingConfiguration
  assignments_count: integer
  total_attachments: integer
```

Reglas de `participation → voting`:
- **Mínimo:** se eliminan la regla de 3 inscriptos (`INSUFFICIENT_PARTICIPANTS`) y la de 2
  propuestas. Queda `400 INSUFFICIENT_ATTACHMENTS` con `current_count` y `required_minimum: 3`
  (se reutiliza el code existente). Como hay una propuesta por participante, la cantidad de
  propuestas es igual a la de participantes con propuesta.
- `400 MISSING_VOTING_CONFIG` si falta `voting_config`.
- La configuración se valida con la lógica de `CreateVotingConfiguration` (reutilizada, no
  copiada): `M_EXCEEDS_EVALUABLE`, `MATH_CONSTRAINT_VIOLATION`, y `400 INVALID_THRESHOLDS` si
  `good <= bad` o `good − bad < 0.1`.
- Se valida **todo antes de escribir**. Después, en `db.Transaction`: `UPDATE events` →
  `INSERT voting_configurations` → `INSERT assignments`. Si algo falla: rollback y
  `500 VOTING_SETUP_ERROR`.
- Evaluadores = `participant_id` de las propuestas del evento (`n = k`).

Reglas de `voting → results`: sin cambios en el backend (ya permitía publicar con rankings
faltantes). El cálculo deja de fallar gracias a la migración 023.

**Justificación:** requerimientos 24, 25 y 26 del REQ; DA-4.

**`POST /api/v1/events/{event_id}/voting-config`** (ref: `docs/apis/api.yaml:1112`) y
**`POST /api/v1/events/{event_id}/generate-assignments`** (ref: `docs/apis/api.yaml:1201`)
- **Cambio:** `deprecated: true`. `generate-assignments` usa la misma regla de evaluadores y
  mínimo.
- **Justificación:** un solo camino para abrir la votación, sin dos reglas distintas.

**`POST /api/v1/events/{event_id}/participant/{participant_id}/attachment`** (ref: `docs/apis/api.yaml:931`)
- **Cambio:** se agrega `image/webp` a los tipos permitidos (`attachment_handler.go:218`).
- **Justificación:** el cliente ya lo acepta; el backend no (AC 42 del REQ).

#### Nuevos Endpoints

**`GET /api/v1/events/{event_id}/voting-config/preview`**
- **Servicio:** `api`. Usa `PreviewVotingConfiguration` (`distributed_vote_handler.go:1353`, hoy
  sin ruta), adaptado a GET sin body. Middleware `RequireEventOwner`.
- **Descripción:** resumen del reparto para el diálogo de abrir votación. El front no recalcula
  `m`.
- **Response 200:**
  ```yaml
  data:
    participants_count: integer          # inscriptos
    participants_with_proposal: integer  # k
    can_open_voting: boolean             # k >= 3
    min_m: integer
    max_m: integer                       # k − 1
    recommended_m: integer
    defaults: { quality_good_threshold: 0.6, quality_bad_threshold: 0.3, adjustment_magnitude: 3 }
  ```
- **Errores:** `403` (no es el autor), `404 EVENT_NOT_FOUND`.
- El `min_evaluations_per_file` recomendado es `min(3, m)`; el cliente lo recalcula al mover `m`.

### Cambios de Base de Datos

#### Tablas Existentes a Modificar

**`voting_results`** (ref: `docs/db-schemas/telescopio_db.md`; `migrations/004_constraints_and_triggers.go:231`)
- **Modificar CHECK** `valid_participant_counts`: de
  `total_participants > 0 AND total_votes >= total_participants` a
  `total_participants > 0 AND total_votes >= 0`.
- **Migración 023:** `DROP CONSTRAINT` + `ADD CONSTRAINT`. `Down` restaura el original. Sin
  downtime.
- **Justificación:** sin esto, publicar con rankings faltantes deja el evento en `results` sin
  ranking (el error solo se loguea).

`assignments`, `votes`, `events`, `attachments` y `voting_configurations` no cambian de esquema.
Los triggers no cambian: excluir a quien no tiene propuesta se resuelve eligiendo los evaluadores
en Go, y `validate_assignment_constraints` sigue garantizando que nadie evalúa lo propio (ADR-002).

> Numeración: el REQ reservaba 023 para `notifications` y 024 para este CHECK. Como esta story se
> implementa antes que S-009, se invierte: **023 = CHECK de `voting_results`**, 024 = `notifications`.

### Flujo de Interacción

#### Escenario: Abrir la votación en un solo paso (CA-1 a CA-8)

**Trigger:** la web envía `PATCH /stage` con `stage: "voting"` y `voting_config`.

1. **[api — `UpdateEventStage`]**
   - Valida la transición `participation → voting` y la fecha.
   - `attachments = GetByEventID`; si `len < 3` ⇒ `400 INSUFFICIENT_ATTACHMENTS`.
   - Arma la configuración con defaults (`min_evaluations_per_file = min(3, m)`).
   - Valida umbrales (`INVALID_THRESHOLDS`) y `ValidateVotingConfiguration(config, k, n = k)`.
   - Evaluadores = `participant_id` de las propuestas.
2. **[api]** `db.Transaction`
   - `UPDATE events SET stage = 'voting', voting_estimated_end_date = …`
   - `INSERT voting_configurations`
   - `VotingService.GenerateAssignments(eventID, evaluadores, attachments, config)` →
     `INSERT assignments` (trigger `validate_assignment_constraints`).
3. **[api]** responde `200` con `voting: { configuration, assignments_count, total_attachments }`.
   Después, emails a los inscriptos en segundo plano (sin cambios).

**Outcome:** evento en `voting` con configuración y asignaciones solo para participantes con
propuesta, en una operación.

**Manejo de errores:**
- Configuración inválida → 400 con `code`; la etapa no cambia.
- Falla de escritura → rollback, `500 VOTING_SETUP_ERROR`; el evento sigue en `participation`.

#### Escenario: Publicar con rankings faltantes (CA-12)

1. **[api]** `PATCH /stage { stage: "results" }` → `CalculateAndPersistResults` (quien no completó
   su asignación tiene `Q_i = 0`, ADR-001).
2. **[PostgreSQL]** upsert en `voting_results` que pasa el CHECK relajado.

### Flujos Afectados

- **avance-de-etapa-del-evento** (ref: `docs/flows/avance-de-etapa-del-evento.md`) — Paso 3: body
  con `voting_config` cuando `stage = voting`; el mínimo pasa a 3 propuestas
  (`INSUFFICIENT_ATTACHMENTS`, `required_minimum: 3`); escritura transaccional. Tabla de
  transiciones: `participation → voting` = 3 o más propuestas + configuración. (Los pasos de la
  web los actualiza S-016.)
- **configuracion-y-generacion-de-asignaciones** (ref: `docs/flows/configuracion-y-generacion-de-asignaciones.md`)
  — Paso 1: el `m` recomendado lo calcula solo la api (`GET …/voting-config/preview`). Pasos 2 y
  3: ocurren dentro de `PATCH /stage`; los endpoints quedan `deprecated`. Evaluadores =
  participantes con propuesta. Default `min(3, m)`. Umbrales inválidos: de 500 a
  `400 INVALID_THRESHOLDS`.
- **calculo-y-publicacion-de-resultados** (ref: `docs/flows/calculo-y-publicacion-de-resultados.md`)
  — Paso 5: el CHECK de `voting_results` se relaja.
- **registro-y-carga-de-propuesta** (ref: `docs/flows/registro-y-carga-de-propuesta.md`) — Paso 3:
  el backend suma `image/webp`.

### Consideraciones Técnicas

**Seguridad:**
- La vista previa expone conteos del evento: solo para el autor (`RequireEventOwner`).

**Performance:**
- La transacción toca 3 tablas con decenas de filas; no es una preocupación.

**Riesgos y tests:**
- Hoy los repositorios no reciben transacción (convención `database`). Hace falta un método de
  repositorio o servicio que reciba el `*gorm.DB` de `db.Transaction`.
- Test de integración que fuerza la falla en `INSERT assignments` y verifica que la etapa no
  cambió y no quedó configuración.
- Test de `VotingService` para k = 3, 4 y 10 con el default `min(3, m)`: con `n = k`, cada
  propuesta recibe exactamente `m` evaluaciones si el reparto es perfecto.
- Test de publicación con rankings faltantes que verifica la fila en `voting_results`.

**Dependencias:**
- Ninguna previa. Modifica la regla de S-003 (mínimo de 3 inscriptos).
