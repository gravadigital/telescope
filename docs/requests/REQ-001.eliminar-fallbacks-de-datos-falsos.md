# REQ-001: Eliminar fallbacks de datos falsos ante errores de red

## Requerimiento Original

> FG-1 (crítico) — el frontend fabrica datos falsos ante errores de red (participantes
> inventados, bypass de login silencioso). Todo frontend, sin tocar API.

**Fuente:** Ticket / feature group interno (PRD)
**Fecha de recepción:** 2026-09-21

## Contexto del Producto

**Feature groups relacionados:**
- Feature Group 1: Integridad de lo que el usuario ve — este requerimiento es la captura
  funcional de ese feature group completo.

**Stories relacionadas:**
- Ninguna. Es el primer requerimiento formalizado del producto (no hay stories previas).

**Servicios involucrados:**

## Clarificaciones

### Funcionales

- **P:** El PRD describe el problema como "tres lugares" con datos falsos, pero al revisar
  el código se encontró que la causa raíz está en la capa de servicios (`api.ts`), con más
  puntos afectados de los que el PRD nombra explícitamente — incluyendo un método que ante
  un fallo de red devuelve eventos completamente inventados (con votos y adjuntos falsos)
  que podrían aparecer en el listado de eventos. ¿El alcance incluye corregir toda la capa
  de servicios, o solo los tres puntos que el PRD nombra (login, participantes en
  ManageEventPage, componente Participants)?
- **R:** Toda la capa de servicios. Es la causa raíz: corregir solo los componentes no
  cambia el comportamiento observable porque el servicio ya resuelve con datos falsos o
  vacíos antes de llegar al componente.

- **P:** En el login, el bug real es un catch mal alcanzado: la validación de
  email/password vacío está en el try externo, y cualquier excepción ahí (incluyendo esa
  validación) cae en un catch que loguea al usuario con un token demo falso
  (`demo-token-{timestamp}`) sin mostrar ningún error. ¿Cuál es el comportamiento esperado
  corregido — eliminar el modo demo por completo, o mantenerlo acotado a una caída real de
  la API?
- **R:** Eliminar el modo demo por completo. Las validaciones de formulario deben mostrar
  su error real, y si la API falla por un motivo real, también debe mostrarse un error
  real — nunca loguear con un token fabricado.

- **P:** El PRD menciona como postcondición de este feature group que "el health check de
  Auth refleje el estado real de la API" (hoy está hardcodeado como siempre disponible).
  ¿Esto entra en el alcance de este requerimiento?
- **R:** Sí. Es parte explícita de las postcondiciones del feature group y es de la misma
  familia de problema: un estado fabricado en vez de uno real.

### Alcance

- **P:** ¿Los criterios de aceptación propuestos —que cubren login, las tres cargas de
  datos de `ManageEventPage` (participantes, propuestas, estadísticas de votación), el
  componente `Participants`, y los cuatro métodos de la capa de servicios que fabrican o
  silencian errores— están completos?
- **R:** Aprobados tal cual, sin cambios.

## Requerimientos Funcionales

1. Ningún flujo de la aplicación debe mostrar datos inventados (personas, eventos, cifras)
   como si fueran datos reales cuando una petición al backend falla.
2. Ningún flujo debe mostrar un estado "vacío" (sin participantes, sin propuestas, sin
   votación configurada) cuando en realidad lo que ocurrió fue un fallo de red o del
   servidor — ambos casos deben ser distinguibles para quien usa la aplicación.
3. Ninguna validación de formulario puede ser salteada por un mecanismo de fallback: un
   error de validación debe mostrarse como tal, nunca derivar en un inicio de sesión con
   credenciales fabricadas.
4. El indicador de disponibilidad de la API de autenticación debe reflejar una verificación
   real, no un valor fijo.
5. Cuando una petición falla, la interfaz debe comunicar el fallo de forma visible (mensaje
   de error), reutilizando los mecanismos de error ya existentes en cada pantalla cuando
   estén disponibles.

## Criterios de Aceptación

1. DADO un usuario completó el formulario de login con el email vacío
   CUANDO envía el formulario
   ENTONCES ve el mensaje de error de validación real ("Email is required") y no queda
   logueado.

2. DADO un usuario completa el formulario de login correctamente pero la API de
   autenticación falla por un motivo real (no de validación)
   CUANDO envía el formulario
   ENTONCES ve un mensaje de error real y no queda logueado con un token demo fabricado.

3. DADO un organizador está en la pantalla de gestión de su evento (`ManageEventPage`)
   CUANDO la carga de participantes falla por un error de red o del servidor
   ENTONCES ve un mensaje de error distinguible de "no hay participantes", y no ve la lista
   vacía como si fuera un hecho real del evento.

4. DADO un organizador está en la pantalla de gestión de su evento
   CUANDO la carga de propuestas (attachments) falla
   ENTONCES ve un error visible, y los contadores de propuestas enviadas y el estado por
   participante no se muestran como si todos estuvieran pendientes por un hecho real.

5. DADO un organizador está en la pantalla de gestión de un evento en etapa de votación o
   de resultados
   CUANDO la carga de estadísticas de votación falla
   ENTONCES ve un error visible, distinguible de "la votación aún no fue configurada".

6. DADO cualquier usuario abre el componente que lista participantes de un evento
   CUANDO la carga de participantes falla
   ENTONCES ve el mensaje de error y la lista de participantes queda vacía o no se
   modifica — nunca se rellena con nombres fabricados.

7. DADO cualquier pantalla que liste eventos
   CUANDO la carga del listado de eventos falla por un error de red o del servidor
   ENTONCES la pantalla muestra un estado de error real, y nunca aparecen eventos
   fabricados con datos de votos o propuestas inventados.

8. DADO un usuario navega al detalle de un evento específico
   CUANDO la carga de ese evento falla por un error de red o del servidor
   ENTONCES ve un estado de error real, y nunca se le muestra un evento fabricado, aunque
   el identificador solicitado coincida con uno de los valores usados internamente como
   fallback.

9. DADO un usuario autenticado
   CUANDO la carga de los eventos en los que participa falla por un error de red o del
   servidor
   ENTONCES el sistema distingue "el usuario no está registrado en ningún evento" de "no
   se pudo cargar la información", y no oculta el fallo como una lista vacía silenciosa.

10. DADO cualquier usuario en la pantalla de login
    CUANDO la API de autenticación no está disponible
    ENTONCES el indicador de salud de la API refleja esa caída real, en vez de mostrar
    siempre disponible.

11. DADO un organizador avanza de etapa o cancela un evento desde `ManageEventPage`
    CUANDO la carga de participantes falló silenciosamente antes de esa acción
    ENTONCES el organizador no puede tomar esa decisión sobre datos fabricados o vacíos por
    error — la pantalla ya le mostró que la carga falló antes de permitir la acción.

### Flujo de Interacción

#### Escenario: Login con fallo de validación o de API (AC 1, 2)

**Trigger:** Usuario envía el formulario de login/registro en `AuthForm`

**Flujo (corregido):**

1. **[web — AuthForm.tsx]**
   - Valida `email` y `password` **antes** del `try` que envuelve la llamada a la API (o en
     un `try/catch` propio que no comparte alcance con el de la API).
   - Si falta un campo → `setError("Email is required")` (o el mensaje correspondiente) y
     retorna. **No se ejecuta ninguna llamada a `UserService`.**

2. **[web — AuthForm.tsx, validación pasada]**
   - Acción: `UserService.authenticateUser(email, password)` → `POST
     /api/v1/users/authenticate`
   - Si la API responde error real (credenciales inválidas, servidor caído, red caída):
     `apiRequest` lanza `Error` (ver `error-handling.md`), el `catch` interno ya existente
     (líneas 103-128 de `AuthForm.tsx`) lo captura y hace `setError(errorMessage)`.
   - **Se elimina el `catch` externo que fabrica `demo-token-{timestamp}`** (líneas 132-152
     actuales). No hay login con token fabricado bajo ninguna circunstancia.

**Outcome:** Error de validación o de API real se muestra como mensaje de error; el usuario
nunca queda logueado con una sesión fabricada.

**Manejo de errores:**
- Validación vacía → mensaje de validación real, sin llamar a la API.
- API falla (red, servidor, credenciales) → mensaje de error real, sin login.

#### Escenario: Indicador de salud de la API en el login (AC 10)

**Trigger:** Se monta el componente `Auth`

**Flujo (corregido):**

1. **[web — Auth.tsx]**
   - Acción: `ApiHealthService.checkHealth()` → internamente `GET /health` (ya implementado
     en `config/api.ts:196-204`, sin cambios ahí).
   - `setApiAvailable(isHealthy)` con el resultado real, no `true` hardcodeado.

**Outcome:** El texto "API is not available, running in local mode" (línea 151 de
`Auth.tsx`) refleja una caída real. Nota: dado que el modo demo se elimina (escenario
anterior), este mensaje pasa a ser puramente informativo — no habilita ningún fallback. Se
mantiene porque comunica al usuario por qué el login podría fallar.

**Manejo de errores:**
- Si `/health` no responde o responde `503` → `checkApiHealth()` ya devuelve `false`
  (`config/api.ts:200-203`, `catch` existente). No requiere cambios en `config/api.ts`.

#### Escenario: Carga de eventos y detalle de evento (AC 7, 8, 9)

**Trigger:** Usuario navega a `/events`, a `/events/:eventId`, o se restaura su sesión

**Flujo (corregido):**

1. **[web — EventService.getAllEvents]**
   - Acción: `GET /api/v1/events?limit=100`
   - Si `apiRequest` lanza (red caída, servidor caído, respuesta inválida): **se elimina el
     fallback de 2 eventos fabricados** (líneas 83-111 actuales). El método relanza el error
     (`throw error` en vez de `return [...]`).
   - → `Events.tsx` (`checkApiAndFetchEvents`, ya tiene `try/catch` con `setError`, líneas
     38-56) recibe el error y lo muestra. **No requiere cambios en `Events.tsx`**: ya
     propaga correctamente: el problema estaba 100% en el servicio.

2. **[web — EventService.getEventById]**
   - Acción: `GET /api/v1/events/:id`
   - Si `apiRequest` lanza: **se elimina el fallback que busca en `getAllEvents()`** (líneas
     213-225 actuales). El método relanza el error en vez de devolver `null` silenciosamente
     tras el intento de fallback.
   - Nota: hoy el método ya devuelve `null` como "no encontrado" para el caso de respuesta
     vacía (línea 183-185) — ese camino no cambia, sigue siendo el contrato correcto para
     "no existe". Lo que cambia es que un error de red/servidor real ya no cae en el mismo
     `null` disfrazado de fallback silencioso: se relanza como error para que el caller lo
     distinga.
   - → `EventDetailPage.fetchEventDetails` (línea 91, `catch` existente) y
     `ManageEventPage.loadEventData` (línea 117, `catch` existente) ya diferencian error vs
     `null` en su lógica (`if (!eventData) ... else setError(...)` vs `catch`). **No
     requieren cambios**, salvo que ahora sí van a recibir el error real en vez de nunca
     verlo.

3. **[web — UserService.getUserEvents, invocado por AuthContext.syncUserEvents]**
   - Acción: `GET /api/v1/users/:userId/events`
   - Si `apiRequest` lanza: **se elimina el `return []` del catch** (línea 535 actual). Se
     relanza el error.
   - → `syncUserEvents` (líneas 60-78 de `AuthContext.tsx`) ya tiene su propio `try/catch`
     que hoy solo loguea (`console.error`, línea 76) sin tocar estado. Ver Consideraciones
     Técnicas para la decisión sobre qué hacer con este error a nivel de contexto global.

**Outcome:** Ningún error de red/servidor se disfraza de "lista vacía" ni de "evento
inventado". Las pantallas que ya tenían manejo de error correcto (todas, salvo
`Participants.tsx`) empiezan a recibirlo de verdad.

**Manejo de errores:**
- Fallo real de red/servidor en cualquiera de los tres métodos → se relanza como `Error`,
  cae en el `catch` ya existente de cada caller.
- Respuesta 200 con lista vacía real → sigue siendo lista vacía real (comportamiento
  correcto, no se toca).

#### Escenario: `ManageEventPage` — participantes, adjuntos y estadísticas de votación (AC 3, 4, 5, 11)

**Trigger:** Organizador abre `/events/:eventId/manage`, o el fetch de alguno de los tres
falla tras cargar el evento

**Flujo (corregido):**

1. **[web — ManageEventPage.loadEventData]**
   - Ya carga el evento (`getEventById`) antes de estos tres fetches — sin cambios ahí.
   - **Participantes** (líneas 73-79 actuales): en vez de `catch { setParticipants([]) }`,
     se agrega estado `participantsError: string` y se hace `setParticipantsError(...)`. El
     render (sección "Registered Participants", líneas 534-601) debe distinguir "0
     participantes reales" (mostrar el `empty-state` actual) de "no se pudo cargar" (mostrar
     mensaje de error con opción de reintentar).
   - **Adjuntos** (líneas 82-88 actuales): mismo patrón — `attachmentsError: string` en vez
     de swallow silencioso a `[]`. El contador "Files Submitted" (línea 401-405) no debe
     mostrarse como `0 / N` real si la carga falló.
   - **Estadísticas de votación** (líneas 92-112 actuales): mismo patrón —
     `votingStatsError: string`. La sección "Voting Configuration" (líneas 508-532) no debe
     interpretar el fallo como "votación no configurada": debe mostrar el error.

2. **[web — ManageEventPage.validateStageAdvance, AC 11]**
   - Hoy usa `participants.length` (líneas 226-227, 236-239) para decidir si se puede
     avanzar de etapa. Si la carga de participantes falló y quedó en `[]`, el organizador
     podría avanzar de etapa creyendo que no hay participantes, cuando en realidad no se
     pudo verificar.
   - **Cambio necesario:** `validateStageAdvance` (o `handleAdvanceStageClick`, que la
     invoca indirectamente vía `getNextStage`) debe rechazar el avance de etapa si
     `participantsError` está seteado, con un mensaje explícito ("No se puede avanzar:
     no se pudo verificar la lista de participantes. Reintentá antes de continuar.").

**Outcome:** Un fallo de red al cargar cualquiera de los tres recursos se ve como error
visible y bloquea decisiones que dependan de esos datos (avance de etapa), en vez de
mostrarse como un estado vacío/no-configurado que habilita seguir operando sobre datos
incompletos.

**Manejo de errores:**
- Fallo en participantes/adjuntos/stats → estado de error dedicado por recurso, visible en
  la sección correspondiente, con acción de reintento (recargar `loadEventData` o el fetch
  puntual).
- Avance de etapa bloqueado mientras `participantsError` esté activo.

#### Escenario: `Participants.tsx` — componente de listado (AC 6)

**Trigger:** Cualquier usuario abre el modal de participantes desde `EventDetailPage`

**Flujo (corregido):**

1. **[web — Participants.fetchParticipants]**
   - Se elimina el bloque de `mockParticipants` (líneas 28-55 actuales). El `catch` queda
     solo con `setError('Error loading participants')` (línea 26, ya existe) y **no** llama
     a `setParticipants(...)` con datos fabricados.
   - El render ya tiene un bloque `{error && !loading && (...)}` (líneas 104-111) con botón

     solo dejaba de usarse porque el `catch` pisaba el estado de error con datos falsos
     inmediatamente después.

**Outcome:** Ante un fallo, el modal muestra el mensaje de error y el botón "🔄 Retry" que ya
existe, en vez de una lista de 3 personas inventadas.

**Manejo de errores:**
- Fallo de red/servidor → estado de error visible, `participants` permanece en `[]` (su
  valor inicial, sin modificar).

### Consideraciones Técnicas

#### Riesgos

- **Riesgo:** Al eliminar `getAllEvents()` como fallback de `getEventById()`, cualquier
  código que dependiera implícitamente de ese camino (por ejemplo, para resolver ids de
  eventos demo hardcodeados) deja de funcionar.
  - **Mitigación:** Se confirmó por lectura de `EventDetailPage.tsx` y `ManageEventPage.tsx`
    que ambos ya manejan `null` y error como casos separados y correctos; ninguno depende
    del fallback. Verificar en QA que no queden otras referencias a los dos ids hardcodeados
    (`68a94135-...`, `660e8400-...`) fuera de `api.ts`.

- **Riesgo:** `AuthContext.syncUserEvents` hoy absorbe cualquier error de
  `getUserEvents` sin tocar estado (`catch` en línea 75-77 de `AuthContext.tsx`, solo
  `console.error`). Al dejar de devolver `[]` silenciosamente, el error sigue sin
  propagarse a la UI — el `catch` de `syncUserEvents` ya existe y seguirá absorbiéndolo.
  - **Mitigación:** Esto es aceptable para este requerimiento: `syncUserEvents` corre en
    background (al montar la app y tras login) y no es una pantalla con estado de error
    propio. El requerimiento funcional 2 exige que el fallo sea "distinguible" — no exige
    necesariamente una alerta en pantalla para este caso de sincronización en background.
    Si en el futuro se decide superficiarlo, el punto de extensión es ese mismo `catch` en
    `AuthContext.tsx:75-77`. No se agrega ahora para no exceder el alcance (que es "todo
    frontend, sin tocar API" pero no pide UI nueva de notificaciones globales).

- **Riesgo:** `ManageEventPage` necesita tres estados de error nuevos
  (`participantsError`, `attachmentsError`, `votingStatsError`) además del `error` general
  que ya existe — riesgo de duplicar lógica de render entre los tres.
  - **Mitigación:** Complejidad baja, tres bloques de error condicional siguiendo el mismo
    patrón que `downloadError` (línea 22, ya existente en el mismo archivo) — es el patrón
    establecido en el propio componente, no se introduce uno nuevo.

#### Dependencias

- El fix de `ManageEventPage` (AC 3, 4, 5, 11) depende del fix de la capa de servicios
  (`getEventParticipants`, ya no lanza distinto — sigue devolviendo `[]` en error hoy; el

## Story Split Propuesto

| # | Título | Descripción | Servicios | Dependencias |
|---|--------|-------------|-----------|---------------|
| 1 | Eliminar datos fabricados de la capa de servicios (`api.ts`) | Quitar los fallbacks de eventos y login fabricados: `getAllEvents`, `getEventById`, `getUserEvents` relanzan el error real en vez de devolver datos falsos o listas vacías silenciosas; `AuthForm` deja de loguear con `demo-token`; `Auth` conecta el health check real | web | - |
| 2 | Propagar y mostrar errores reales en pantallas de gestión y listado | `ManageEventPage` distingue error de "vacío" en participantes, adjuntos y estadísticas de votación (y bloquea el avance de etapa si no pudo verificar participantes); `Participants.tsx` deja de rellenar con datos inventados ante un fallo | web | Story 1 |

**Orden de implementación sugerido:**
1. **Eliminar datos fabricados de la capa de servicios** — es la causa raíz: mientras
   `getAllEvents`/`getEventById`/`getUserEvents` sigan devolviendo datos fabricados o listas
   vacías silenciosas ante un error, ningún cambio en los componentes que los consumen puede
   mostrar el error real. También cubre el login (AC 1, 2) y el health check (AC 10), que son
   independientes de la capa de eventos pero igual de simples de resolver primero.
2. **Propagar y mostrar errores reales en pantallas** — una vez que el servicio relanza
   errores reales (o, en el caso de participantes, una vez confirmado que ya lo hacía),
   recién tiene sentido agregar los estados de error dedicados y la lógica de bloqueo en
   `ManageEventPage` y limpiar el fallback local de `Participants.tsx`.
