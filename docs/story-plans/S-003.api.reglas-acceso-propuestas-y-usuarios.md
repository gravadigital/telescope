# Story Plan: S-003 (api) - Reglas de acceso a propuestas y a datos de usuario

## Status

**Status:** Completed

## Story Reference

- **Story:** [S-003](../stories/S-003.reglas-acceso-propuestas-y-usuarios.md)
- **Service:** api
- **Summary:** El evaluador puede descargar las propuestas de su Asignación mientras el evento
  está en `voting` y sin cancelar (corrige D-15 del lado `api`). Además, `GET /users/{user_id}`
  queda restringido al propio usuario y al autor de un evento en el que participa el consultado
  (corrige D-03).

### Decisiones tomadas al planificar (aprobadas por el usuario)

1. **`RequireSelfOrEventCreator` no tiene bypass de `admin`.** El diseño de la story no lo
   lista, y S-005 retira el rol global: no se agrega código que la próxima story tiene que
   borrar. Consecuencia aceptada: hasta S-005, un `admin` no lee datos de usuarios ajenos.
2. **La rama de evaluador de `canDownload` falla cerrada.** Cualquier error de
   `GetAssignmentByParticipant` (no solo "no encontrado") equivale a `false` y termina en
   `403 FORBIDDEN`, igual que hoy se trata el error de `eventRepo.GetByID`. `canDownload`
   sigue devolviendo `bool`.
3. **El spec ya está actualizado.** `docs/apis/api.yaml` ya documenta los cambios de S-003
   (`MiddlewareBadRequest`, `INTERNAL_ERROR` en el enum de `MiddlewareError`, descripciones
   nuevas del `403` y del `404`). No hay tarea sobre el spec; la implementación tiene que
   coincidir con lo que ya dice.
4. **Los tests del middleware viven en el paquete `auth`**, con un fake propio de
   `EventRepository`: los mocks de `internal/handlers` son archivos `_test.go` de otro paquete
   y no se pueden importar.

**Reglas de `_base` (Go) aplicables:**
- No hay estado global mutable. Las dependencias se pasan explícitamente, con wiring manual en
  `cmd/{service}/` y sin framework de DI.
- Se aceptan interfaces y se devuelven structs.
- Errores: wrapping con `fmt.Errorf("...: %w", err)` e inspección con `errors.Is`/`errors.As`.
- `panic` nunca.
- Comentarios: por defecto ninguno. Los identificadores exportados llevan doc comment que
  empieza con su nombre, y solo se comenta el *por qué* cuando no es obvio.
- Acrónimos conservan el caso (`userID`, `eventID`, `HTTP`).

**`http-server` (custom, Gin):**
- Un handler es un método sobre un struct que recibe sus dependencias **por constructor**.
- **Todas las rutas se registran en `cmd/api/main.go`**, en el grupo que corresponda.
- Los permisos se componen declarándolos en la ruta, no dentro del handler.
- Nunca `uuid.MustParse` sobre entrada del usuario: `uuid.Parse` y `400` si falla.
- El middleware global `events.CreateEvent()` ya loguea cada request: no se agrega logging de
  entrada/salida en handlers ni middlewares.

**Error handling (`error-handling`, custom):**

- **Forma A** (handlers, la de `DownloadAttachment`):
  `{ "error": "Mensaje legible", "code": "SCREAMING_SNAKE", "details": "..." }`
- **Forma B** (middlewares de auth y permisos, la de `RequireSelfOrEventCreator`):
  `{ "error": "UNAUTHORIZED", "message": "Missing Authorization header" }`. En esta forma
  `error` es el **código** y el texto va en `message`; **nunca trae `code`**.
- **Reglas para código nuevo:**
  1. En handlers se usa la forma A, siempre con `code`.
  2. No se inventan `code` nuevos si ya existe uno equivalente.
  3. El status HTTP coincide con la semántica: `401` solo para credenciales ausentes o
     inválidas, `403` para autenticado sin permiso, `404` para inexistente, `400` para
     entrada inválida.
  4. **No se exponen errores internos crudos.** Se loguea el error real y se devuelve un
     mensaje controlado.

**Testing (`testing`, custom):**
- Los tests unitarios no necesitan base ni red: `go test ./...`. Desde la raíz del repo,
  `make test` corre `go vet` + `go test -race ./...` (y los tests de web).
- Los mocks se escriben a mano en archivos `mocks_*_test.go`. **Al agregar un método a una
  interfaz de repositorio, hay que agregarlo también al mock** o el paquete de tests deja de
  compilar.
- Los tests de handler se escriben contra `gin.Context` de test (`gin.CreateTestContext`) o
  contra un router `gin.New()` en `gin.TestMode` con `httptest`.
- Table-driven, un subtest por caso con `t.Run`. `assert` para seguir tras el fallo y
  `require` cuando el resto del test no tendría sentido.
- **Se verifica el `code` del error, no solo el status** (en la forma B, se verifica `error`).
- "Qué falta" (estado previo): los middlewares de `internal/middleware/auth` no tienen tests.
  Esta story agrega los primeros.

### Relevant ADRs

- **ADR-004: Gin y GORM**
  - Decisión: Gin 1.10.1 como framework HTTP y GORM 1.30.2 como ORM. El wiring de
    dependencias es manual y explícito en `cmd/api/main.go`, sin framework de inyección.
  - Implementado en `api`: `cmd/api/main.go` arma todo el router, y
    `internal/storage/postgres/` contiene los repositorios.
  - Aplica a: el cambio de firma de `NewAttachmentHandler` se cablea a mano en `main.go`.

- **ADR-005: Entidades de dominio como contrato JSON**
  - Decisión: las structs de dominio llevan los tags de GORM y los de JSON en el mismo campo,
    sin capa de DTOs.
  - Aplica a: `vote.Assignment.AttachmentIDs` es `pq.StringArray` (un `[]string`), mapeado a
    `uuid[]`. La comparación con `att.ID` se hace con `att.ID.String()`.

- **ADR-002: Reglas de negocio en triggers**
  - Decisión: parte de las invariantes están en triggers plpgsql. Entre ellas,
    `validate_assignment_constraints` hace que **nadie tenga asignada su propia propuesta**.
  - Aplica a: la rama de evaluador no necesita excluir al dueño, porque el dueño ya pasa por su
    propia rama antes y la asignación no puede contenerlo.

### API Context

La autenticación es `auth.JWTAuthMiddleware()`, que espera `Authorization: Bearer <token>`. Deja
en el contexto:
- `user_id`, como `string`
- `user_email`
- `user_role`, como `participant.Role`

Helpers:

```go
userID, err := auth.GetUserIDFromContext(c)   // uuid.UUID
role, err := auth.GetUserRoleFromContext(c)   // participant.Role
```

Cuando falla, `JWTAuthMiddleware` responde `401` con la forma B:
- Sin header: `{"error":"UNAUTHORIZED","message":"Missing Authorization header"}`.
- Header mal formado o token inválido: `401 UNAUTHORIZED` con otro `message`.

**Modelo de roles en dos niveles:**

| Nivel | Dónde | Valores | Para qué |
|---|---|---|---|
| **Global** | `users.role`, va en el JWT | `admin`, `organizer`, `participant` | Capacidades del sistema |
| **Por evento** | `event_participants.role` | `creator`, `participant` | Quién manda en *este* evento |

La autoría del evento se verifica contra `events.author_id`, no contra el rol global.

**Reglas al agregar endpoints (`auth-jwt`):**
1. Verificá en qué grupo registrás la ruta. Fuera del grupo con `JWTAuthMiddleware()` el
   endpoint queda público.
2. Autenticado no es autorizado. Si el recurso pertenece a alguien, sumá el middleware de
   permiso.
3. **La verificación de permisos va en el middleware, no en el handler**, salvo que dependa del
   body. La descarga es la excepción documentada: el evento se deriva del attachment, así que
   se verifica en `canDownload`.

#### `GET /api/v1/attachments/{attachment_id}/download` (spec vigente)

```yaml
description: |
  Pueden descargarla:
  - su dueño (`attachments.participant_id`), en cualquier etapa;
  - el autor del evento (`events.author_id`), en cualquier etapa;
  - el evaluador que la tiene en `assignments.attachment_ids` de su asignación en ese
    evento, solo con `events.stage = voting` y `events.is_cancelled = false`.
    `is_paused` no afecta, y tampoco `assignments.is_completed` (S-003, corrige D-15).

  El permiso se verifica en el handler (`canDownload`), no con un middleware de ruta:
  el evento se deriva del attachment. S-005 retira el acceso por rol `admin`.
responses:
  '200':  # binario. Headers: Content-Disposition: attachment; filename="<nombre original>", Content-Type, Content-Length
  '401': { $ref: '#/components/responses/MiddlewareUnauthorized' }
  '403':
    description: '`FORBIDDEN` — no es el dueño, ni el autor del evento, ni tiene la propuesta en su asignación con el evento en `voting` y sin cancelar'
    content: { application/json: { schema: { $ref: '#/components/schemas/ApiError' } } }
  '404':
    description: '`ATTACHMENT_NOT_FOUND`, `FILE_NOT_FOUND`'
```

Rutas actuales (`cmd/api/main.go`):

```go

{
```

### Flow Context

**`evaluacion-y-envio-de-ranking` — Paso 1b: Abrir una propuesta asignada** (ya documentado en el
flujo, lo implementa esta story del lado `api`)

> **Origen:** `web` · **Destino:** `api` · **Tipo:** REST · **Stories:** S-003 (regla), S-004 (panel)
>
> - **Método:** GET
> - **Endpoint:** `/api/v1/attachments/{attachment_id}/download`
> - **Auth:** JWT Bearer — `RankingVotePanel` usa `AttachmentService.downloadAttachment`, no un
>   `<a href>`
>
> **Response (éxito) — 200:** el archivo binario con `Content-Disposition`, `Content-Type` y
> `Content-Length`.
>
> **Operaciones de BD:** `SELECT` sobre `attachments` por `id`; `SELECT` sobre `events` por
> `attachments.event_id`; si el usuario no es dueño ni autor, `SELECT` sobre `assignments` por
> (`event_id`, `participant_id`).
>
> **Regla de evaluador (`canDownload`):** permite si `events.stage = voting`,
> `events.is_cancelled = false` y `attachment_id ∈ assignments.attachment_ids`. `is_paused` no
> afecta, y tampoco `assignments.is_completed`: el evaluador puede volver a abrir sus propuestas
> después de enviar el ranking, mientras dure `voting`. Se evalúa en cada descarga.

Manejo de errores del paso 1b:

| Paso | Condición | Respuesta |
|---|---|---|
| 1b | Propuesta fuera de la asignación, evento en `results` o cancelado | 403 `FORBIDDEN` |
| 1b | Attachment o archivo inexistente | 404 `ATTACHMENT_NOT_FOUND` / `FILE_NOT_FOUND` |

**`avance-de-etapa-del-evento`**. Lo que implica esta story:
- `voting → results`: **cierra la descarga de propuestas de los evaluadores** (S-003).
- Cancelar (`PATCH /api/v1/events/{event_id}/cancel`): en `voting`, cierra la descarga de
  propuestas de los evaluadores (S-003).

No se agrega código en el avance de etapa. El cierre sale solo, porque la regla se evalúa en
cada descarga contra `events.stage` y `events.is_cancelled`, sin estado cacheado.

### Code Conventions

- Handlers en `internal/handlers/{area}_handler.go`. Receiver `h`. Logger con
  `logger.Handler("attachment")` (el handler actual ya lo tiene).
- Middlewares de permiso en `internal/middleware/auth/permissions.go`, como funciones
  `RequireXxx(deps) gin.HandlerFunc` que devuelven una closure. Cortan con `c.JSON(...)` +
  `c.Abort()` + `return`, y siguen con `c.Next()`.
- Repositorios en `internal/storage/postgres/{entidad}_repository.go`, con receiver `r`,
  logger `r.log`. Siguen el patrón de log Debug al entrar y Error al fallar.
- Tests: `Test{Unidad}_{Comportamiento}` (por ejemplo, `TestDownloadAttachment_AllowsAssignedEvaluator`).

**`canDownload` actual** (`internal/handlers/attachment_handler.go`)

```go
func (h *AttachmentHandler) canDownload(c *gin.Context, att *attachment.Attachment) bool {
    userID, err := auth.GetUserIDFromContext(c)
    if err != nil {
        return false
    }

    if role, err := auth.GetUserRoleFromContext(c); err == nil && role == participant.RoleAdmin {
        return true
    }

    if att.ParticipantID == userID {
        return true
    }

    eventEntity, err := h.eventRepo.GetByID(att.EventID.String())
    if err != nil {
        return false
    }

    return eventEntity.AuthorID == userID
}
```

```go
// IsCreatorOfEventWithParticipant reports whether creatorID authored at least one
// event in which userID has an event_participants row, in any stage.
func (r *PostgresEventRepository) IsCreatorOfEventWithParticipant(creatorID, userID string) (bool, error) {
    // uuid.Parse de ambos → error wrapeado si falla
    var exists bool
    err := r.db.Raw(`SELECT EXISTS (
        SELECT 1 FROM events e
        JOIN event_participants ep ON ep.event_id = e.id
        WHERE e.author_id = ? AND ep.user_id = ?
    )`, creatorUUID, userUUID).Scan(&exists).Error
    // ...
}
```

- GORM usa `?` como placeholder en `Raw`; el `$1`/`$2` del diseño es la forma SQL equivalente.
- Si el usuario ya existe en `users` pero nunca participó, el resultado es `false`.
