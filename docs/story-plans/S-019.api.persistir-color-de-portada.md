# Story Plan: S-019 (api) - Persistir el color de portada y destrabar la edición de eventos viejos

## Status

**Status:** Ready

## Story Reference

- **Story:** [S-019](../stories/S-019.persistir-color-de-portada.md)
- **Service:** api
- **Source:** [REQ-004](../requests/REQ-004.marco-de-plataforma-y-color-de-portada-del-evento.md)
- **Summary:** el evento guarda `cover_color`, uno de 16 identificadores de una paleta cerrada
  (default `lavender`). Se elige al crear (`POST /events`) y se cambia con
  `PATCH /events/{event_id}`; si el body trae **solo** `cover_color`, se acepta en cualquier etapa y
  estado. Incluye reemplazar el CHECK `future_start_date`, que hoy rompe cualquier UPDATE de un evento
  con `start_date` anterior a ayer (deuda #10 de `api`).

**Reglas de las convenciones activas:**

- **`_base`:** `gofumpt`; constantes `MixedCaps`; errores envueltos con `%w`; sin `panic`; sin estado
  global mutable (solo constantes y errores centinela a nivel de paquete); identificadores exportados
  con doc comment; comentarios solo para el *por qué*.
- **`http-server`:** rutas en `cmd/api/main.go`; nunca `uuid.MustParse` sobre entrada del usuario;
  envelope de éxito `data` en endpoints nuevos (en `POST /events` el envelope heredado `event` **no se
  cambia**); payload de respuesta construido explícitamente.
- **`validation`:** orden fijo: (1) path params a mano, (2) body con binding, (3) reglas de negocio
  a mano. Las invariantes de dominio van en la entidad.
- **`error-handling`:** forma A `{ "error": "<mensaje>", "code": "SCREAMING_SNAKE", "details": "<string>" }`;
  `details` string; status según semántica (`400` entrada inválida, `403` sin permiso, `409` conflicto
  de estado); no exponer errores internos.
- **`database`:** si agregás un campo a una entidad, agregá su migración (no alcanza el tag);
  migraciones Go con `Up`/`Down`, numeración de tres dígitos, registradas en orden; repositorios con
  IDs `string` y sin `context.Context`; no usar la variable global `postgres.DB`.
- **`testing`:** table-driven con `t.Run`; `require` cuando el resto no tiene sentido; **verificar el
  `code` del error, no solo el status**; al agregar un método a un repositorio, agregarlo al mock.
  Integración detrás de `//go:build integration`, base `TEST_DB_NAME` (`make test-integration` crea
  `telescope_test`).

### Task 2: Migración `025` — columna, CHECK y trigger de fecha

**Status:** Completed

#### Description

Agregar `cover_color` y reemplazar el CHECK `future_start_date` por un trigger que solo actúe al
crear el evento o al cambiar su `start_date`.

#### Acceptance Criteria

1. `internal/storage/migrations/025_add_cover_color_and_start_date_trigger.go` con `migration025Up` y
   `migration025Down`, registrada como `{ID: "025", Name: "add_cover_color_and_start_date_trigger"}`
   después de la `024`.
2. `Up`, en orden:
   - `ALTER TABLE events ADD COLUMN IF NOT EXISTS cover_color VARCHAR(32) NOT NULL DEFAULT 'lavender'`
   - `ALTER TABLE events ADD CONSTRAINT valid_cover_color CHECK (cover_color IN ('lavender','periwinkle','sky','ice','aqua','mint','pistachio','lemon','butter','peach','coral','rose','pink','lilac','sand','mist'))`
   - `ALTER TABLE events DROP CONSTRAINT IF EXISTS future_start_date`
   - `CREATE OR REPLACE FUNCTION enforce_future_start_date() RETURNS trigger LANGUAGE plpgsql`: si
     `TG_OP = 'INSERT' OR NEW.start_date IS DISTINCT FROM OLD.start_date`, y
     `NEW.start_date < CURRENT_TIMESTAMP - INTERVAL '1 day'`, `RAISE EXCEPTION 'start_date cannot be in the past'`;
     devuelve `NEW`.
   - `CREATE TRIGGER enforce_future_start_date BEFORE INSERT OR UPDATE OF start_date ON events FOR EACH ROW EXECUTE FUNCTION enforce_future_start_date()`
3. `Down`: `DROP TRIGGER IF EXISTS enforce_future_start_date ON events`,
   `DROP FUNCTION IF EXISTS enforce_future_start_date()`, `ADD CONSTRAINT future_start_date CHECK
   (start_date >= CURRENT_TIMESTAMP - INTERVAL '1 day') NOT VALID`, `DROP CONSTRAINT IF EXISTS
   valid_cover_color`, `DROP COLUMN IF EXISTS cover_color`.
4. `TestEventUpdate_FutureStartDateCheckOnOldEvent` invertido: el UPDATE del evento viejo ya no
   falla; actualizar su comentario.

#### Technical Details

- **Contexto:** convención `database` (migraciones); ADR-002; "Database Context".
- **Archivos:** migración nueva + `migrations.go`;
  `025_add_cover_color_and_start_date_trigger_integration_test.go` (nuevo, paquete `migrations`, usa
  `migratedTx`); `internal/storage/postgres/batch_queries_integration_test.go`.
- **Notas:** `IS DISTINCT FROM` es imprescindible: `EventRepository.Update` es un `Save` de GORM que

  constraint; con la `025` aplicada, para insertarlo hay que deshabilitar el trigger

### Task 4: `UpdateEvent` acepta `cover_color` con excepción de etapa

**Status:** Completed

#### Description

Cambiar el color por `PATCH /events/{event_id}` en cualquier etapa cuando es el único campo.

#### Acceptance Criteria

1. `UpdateEventRequest` suma `CoverColor *string \`json:"cover_color"\``.
2. `validateUpdateEventRequest`: el "al menos un campo" incluye `cover_color` (mensaje:
   `"at least one of name, description, organizer, max_participants, cover_color is required"`);
   un `cover_color` no válido produce `400 INVALID_COVER_COLOR` (no `INVALID_PAYLOAD`).
3. La regla de etapa se aplica solo si `Name`, `Description`, `Organizer` o `MaxParticipants` vienen
   no nulos. Con solo `CoverColor`, se saltea.
4. Si viene `CoverColor`, se asigna a `existingEvent.CoverColor` antes de `Update`.
5. Sin chequeos de `IsPaused` / `IsCancelled` para el color.

#### Technical Details

- **Contexto:** `validation` (orden de capas), `error-handling`, flujo
  `edicion-y-visibilidad-del-evento` paso 3.
- **Archivos:** `internal/handlers/event_handler.go`, `internal/handlers/event_list_update_test.go`.
