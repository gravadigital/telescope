# Story Plan: S-006 (api) - Apertura de votación atómica y reglas de avance

## Status

**Status:** In Progress

## Story Reference

- **Story:** [S-006](../stories/S-006.apertura-de-votacion-atomica.md)
- **Service:** api
- **Summary:** Que `PATCH /stage` con `stage: "voting"` avance la etapa, guarde la configuración
  y genere las asignaciones —solo para participantes con propuesta— en una única transacción, con
  mínimo de 3 propuestas y validaciones que devuelven `400` con `code` en vez de `500`. Suma la
  vista previa del reparto (`GET /voting-config/preview`), relaja el CHECK de `voting_results`
  para publicar con rankings faltantes y acepta `image/webp`.

### Decisiones tomadas al planificar (aprobadas por el usuario)

| # | Tema | Decisión |
|---|---|---|
| D1 | `PATCH /stage → voting` sobre un evento que **ya tiene** `voting_configurations` (creada con el `POST /voting-config` deprecado durante `participation`) | **Se reemplaza dentro de la misma transacción** (se reutiliza el `id` existente y se hace `Update`). Todavía no hay asignaciones, así que no se pierde nada. Rechazar con 409 dejaría el evento trabado en el estado intermedio que esta story elimina |
| D2 | Definición de `min_m` y `recommended_m` | Una sola función `vote.VotingBounds(k)`. `maxM = max(k−1, 0)`. `recommendedM = min(⌈2·log₂k⌉, maxM)` (la fórmula que hoy tiene el front en `VotingConfigurationPanel.tsx:25-31`, que se elimina en S-016). `minM` = el mínimo que ya acepta `ValidateVotingConfiguration`: `recommendedM`, relajado a `⌈0.6·maxM⌉` cuando `k ≤ 10` |

| D5 | Umbrales en `voting_config` | Se reciben como `*float64` (y `*int` para `adjustment_magnitude` y `min_evaluations_per_file`): `nil` toma el default y un `0` explícito se respeta |

**Handlers (convención `http-server`):**

- Un handler es un método sobre un struct que recibe sus dependencias por constructor. Orden
  interno: 1. path params 2. body 3. reglas de negocio 4. respuesta.
- El handler **no** contiene el algoritmo de negocio: parsea, delega y responde. La lógica de
  votación vive en `internal/domain/vote/`.
- Nunca `panic`. Nunca `uuid.MustParse` sobre entrada del usuario: `uuid.Parse` y `400` si falla.
- **Todas las rutas se registran en `cmd/api/main.go`**, en el grupo correcto. Un endpoint
  declarado fuera del grupo con `.Use(auth.JWTAuthMiddleware())` queda **público**.
- Éxito: envelope `data`. **Nunca serializar una entidad de dominio directo**: construir el
  payload de respuesta explícitamente.
- No agregar logging de entrada/salida de requests: ya lo hace `events.CreateEvent()`.

**Validación (convención `validation`) — tres capas, en este orden:**

1. Path params manual (`MISSING_EVENT_ID`, `INVALID_EVENT_ID`).
2. Body con binding tags de Gin (`INVALID_PAYLOAD` + `details: err.Error()`).
   - `min`/`max` sin `required` sobre tipos valor no funcionan: un `float64` ausente llega como
     `0`. Para campos opcionales con default, documentar el default y aplicarlo explícitamente.
     Por eso D5 usa punteros.
   - Un struct anidado no nulo se valida automáticamente (el validador entra en structs y
     punteros a struct).
3. Reglas de negocio, manual. La validación de invariantes del dominio va en el dominio, no en
   el handler; el handler la invoca. `VotingService.ValidateVotingConfiguration` valida las
   restricciones matemáticas antes de tocar la base.
- Las reglas que imponen los triggers conviene validarlas también en Go **antes**, porque el
  error del trigger llega como `500` crudo.

**Manejo de errores (convención `error-handling`):**

- Forma A, siempre con `code`: `{ "error": "mensaje legible", "code": "SCREAMING_SNAKE", "details": "string opcional" }`.
- No inventar `code` nuevos si ya existe uno equivalente. `details` siempre string.
- Status: `400` entrada inválida, `403` sin permiso, `404` inexistente, `409` conflicto, `500` interno.
- No exponer errores internos crudos: loguear el real y devolver un mensaje controlado.

```go
if err != nil {
    h.log.Error("failed to create event", "error", err)
    c.JSON(http.StatusInternalServerError, gin.H{
        "error": "Failed to create event",
        "code":  "DB_CREATE_ERROR",
    })
    return
}
```

- Entre capas: `fmt.Errorf("...: %w", err)`; inspección con `errors.Is` / `errors.As`. Para
  distinguir un caso, definir un error centinela en el paquete del módulo (prefijo `Err`).
- Los middlewares de permisos responden con la forma B: `{ "error": "FORBIDDEN", "message": "..." }`.

**Logging (convención `logging`):** siempre pares clave-valor
(`h.log.Error("failed to open voting", "error", err, "event_id", eventID)`); logger por
componente obtenido en el constructor (`logger.Handler("event")`). No loguear tokens ni la
connection string.

**Base (`_base`):** `gofumpt`; sin estado global mutable (no usar `postgres.DB`); constantes
`MixedCaps`; errores centinela con prefijo `Err`; comentarios solo para el "por qué"; `// TODO`
solo con issue asociado.

### Relevant ADRs

**ADR-001: Votación distribuida por pares con Modified Borda Count**
- Decisión: modelo de Merrifield & Saari (2009) en `internal/domain/vote/voting_service.go`.
  1. **Asignación** — cada uno de los `n` participantes recibe `m` propuestas de las `k` totales.
     Nadie recibe la propia (`m ≤ k−1`). Se exige `m ≥ 2·log₂(k)` como condición de
     convergencia, relajada al 60% del máximo posible cuando `k ≤ 10`.
  2. **MBC** — `MBC(f_j) = (1/(m(m−1))) · Σ(m − R_i(f_j))`, normalizado a `[0,1]`.
  3. **Calidad del evaluador** — `Q_i = 1 − (2/(m(m−1))) · Σ|R_i(f_j) − RelativeRank_G(f_j, A(p_i))|`.
     **Quien no completa su asignación recibe `Q_i = 0`.**
  4. **Incentivos** — la propuesta de un evaluador con `Q_i ≥ quality_good_threshold` sube `n`
    posiciones; con `Q_i ≤ quality_bad_threshold` baja `n`.
- Aplica a esta story: con evaluadores = participantes con propuesta, `n = k`, y la cobertura
  `n·m ≥ k·min_evaluations_per_file` se reduce a `m ≥ min_evaluations_per_file`. Por eso el
  default pasa a `min(3, m)`.
- Consecuencia conocida (D-10): `min_evaluations_per_file` puede no alcanzarse en silencio,
  porque la fase 1 respeta el tope `m` por participante.

**ADR-002: Reglas de negocio implementadas en triggers de PostgreSQL**
- Decisión: invariantes en plpgsql (`004_constraints_and_triggers.go`, funciones recreadas en
  `022`).

| Regla | Mecanismo |
|---|---|
| La asignación debe tener exactamente `m` attachments | `validate_assignment_constraints` (BEFORE INSERT/UPDATE) |
| Los attachments deben existir y pertenecer al evento | `validate_assignment_constraints` |
| **Nadie puede evaluar su propia propuesta** | `validate_assignment_constraints` |
| El votante debe tener una asignación en el evento | `validate_vote_constraints` (BEFORE INSERT/UPDATE) |
| Solo se vota lo que está en la propia asignación | `validate_vote_constraints` |
| `rank_position ≤ attachments_per_evaluator` | `validate_vote_constraints` |
| Cálculo del score Borda si viene nulo | `validate_vote_constraints` |
| Marcado de asignación completa | `update_assignment_completion` (AFTER INSERT/DELETE) |
| Mantenimiento de `attachments.vote_count` | `update_attachment_vote_count` (AFTER INSERT/DELETE) |

- **Recomendación del ADR (regla a cumplir):** antes de modificar cualquier regla de asignación o
  votación, leer `internal/storage/migrations/004_constraints_and_triggers.go`. **Si la regla
  existe en los dos lados, cambiar los dos en la misma story.**
- Aplica a esta story: excluir a quien no tiene propuesta se resuelve **eligiendo los
  evaluadores en Go**; los triggers no cambian. `validate_assignment_constraints` busca la
  configuración del evento con `SELECT * FROM voting_configurations WHERE event_id = NEW.event_id`:
  dentro de la transacción ve la configuración recién insertada, así que el orden
  `INSERT voting_configurations` → `INSERT assignments` es obligatorio.

**ADR-005: Las entidades de dominio son a la vez modelo de persistencia y contrato JSON**
- Decisión: las structs de dominio llevan tags GORM y JSON en el mismo campo, sin DTOs.
- Aplica a esta story: en código nuevo, el payload de respuesta (`voting.configuration`,
  `data` de la vista previa) se arma con `gin.H` explícito, no serializando
  `vote.VotingConfiguration`.

### API Context

**`PATCH /api/v1/events/{event_id}/stage`** — `RequireEventOwner` (autor o `admin`). Spec
actualizado (`docs/apis/api.yaml`):

Request:
```yaml

  quality_good_threshold: number      # opt, 0..1, default 0.6
  quality_bad_threshold: number       # opt, 0..1, default 0.3
  adjustment_magnitude: integer       # opt, 1..10, default 3

```

Response 200:
```yaml

  id: uuid
  name: string
  description: string

  end_date: date
  stage: Stage
```

Errores:
- `400`: `MISSING_EVENT_ID`, `INVALID_EVENT_ID`, `INVALID_PAYLOAD`, `INVALID_STAGE`,
  `INVALID_TRANSITION` (+ `current_stage`, `requested_stage`), `MISSING_ESTIMATED_DATE`,
  `INVALID_DATE_FORMAT`, `INVALID_ESTIMATED_DATE`, `INSUFFICIENT_ATTACHMENTS`
  (+ `current_count`, `required_minimum: 3`), `MISSING_VOTING_CONFIG`, `INVALID_THRESHOLDS`,
  `M_EXCEEDS_EVALUABLE`, `MATH_CONSTRAINT_VIOLATION`. (`INSUFFICIENT_PARTICIPANTS` y
  `NO_ATTACHMENTS` dejan de usarse en esta transición.)
- `401`/`403`: middleware (forma B).
- `404`: `EVENT_NOT_FOUND`.
- `500`: `PARTICIPANTS_ERROR`, `ATTACHMENTS_ERROR`, `DB_UPDATE_ERROR`, `RETRIEVAL_ERROR`,
  `VOTING_SETUP_ERROR`.

Comportamiento descrito en el spec:
- Pasar a `voting` exige **al menos 3 participantes con propuesta** y `voting_config`. Se valida
  todo antes de escribir y, en una transacción, se actualiza la etapa, se guarda la
  configuración y se generan las asignaciones **solo para participantes con propuesta**. Si la
  escritura falla → rollback y `500 VOTING_SETUP_ERROR`; el evento sigue en `participation`.
- Pasar a `results` calcula el ranking MBC y lo guarda en `voting_results`, también con
  rankings faltantes (CHECK relajado, migración 023). Si el cálculo falla, el cambio de etapa
  igual se aplica y el error solo queda en el log.
- Dispara emails a los participantes en segundo plano.

### Database Context

**`events`** (relevante): `id uuid PK`, `stage event_stage NOT NULL default creation`,
`participation_estimated_end_date date null`, `voting_estimated_end_date date null`. Lo actualiza
`EventRepository.UpdateStageWithEstimatedDate(eventID string, stage event.Stage, estimatedDate *time.Time) error`.

**`attachments`**: una por participante por evento (regla de la aplicación). `id`, `event_id`,
`participant_id uuid NOT NULL FK users.id`, `mime_type varchar(100)`, `file_size` CHECK 1..100MB,
`vote_count` (lo mantiene un trigger).

**`voting_configurations`**: una por evento (`event_id` UNIQUE).

| Columna | Tipo | Restricciones |
|---|---|---|
| `attachments_per_evaluator` | `integer` | NOT NULL, CHECK entre 1 y 50. Parámetro `m` |
| `min_evaluations_per_file` | `integer` | NOT NULL, default 3, CHECK > 0 |
| `quality_good_threshold` | `decimal(3,2)` | Q_good |
| `quality_bad_threshold` | `decimal(3,2)` | Q_bad |
| `adjustment_magnitude` | `integer` | CHECK entre 0 y 20. Parámetro `n` |

CHECK `valid_quality_thresholds`: `quality_good_threshold > quality_bad_threshold AND
quality_good_threshold - quality_bad_threshold >= 0.1`. La base guarda centésimas: la
validación en Go compara en centésimas (`math.Round(x*100)`).

**`assignments`**: `id`, `event_id`, `participant_id uuid FK users.id`, `attachment_ids uuid[]`
(`pq.StringArray`), `assignment_round` default 1, `is_completed` (trigger), `quality_score`
decimal(5,4) null. **S-006:** solo los participantes con propuesta reciben asignación; se insertan
en la misma transacción que el paso a `voting` y la configuración.

**`voting_results`**: una por evento (`event_id` UNIQUE). `global_ranking jsonb`,
`participant_qualities jsonb`, `adjusted_ranking jsonb`, `total_participants integer`,
`total_votes integer`, `attachments_per_evaluator integer`.
- CHECK actual (`004_constraints_and_triggers.go:231`):
  `valid_participant_counts CHECK (total_participants > 0 AND total_votes >= total_participants)`.
- **Migración 023 (esta story):** `total_participants > 0 AND total_votes >= 0`.
- Por qué: `CalculateModifiedBordaCount` guarda `TotalParticipants = len(participantQualities)`
  (`voting_service.go:259`) y `TotalVotes = cantidad de votos`. Con rankings faltantes,
  `total_votes < total_participants`, el upsert falla y el evento queda en `results` sin ranking
  (el error solo se loguea).
- También existe `valid_evaluator_counts` sobre columnas que el dominio no escribe; pasa
  trivialmente. No se toca.

**Triggers** — `validate_assignment_constraints` (BEFORE INSERT OR UPDATE ON `assignments`), si
el evento tiene configuración: 1) cantidad de `attachment_ids` **exactamente**
`attachments_per_evaluator`; 2) todos existen y son del evento; 3) **ninguno es del propio
participante**. Una violación llega como `RAISE EXCEPTION` de plpgsql → error crudo del driver.

**Migraciones** — Go, no SQL. Par `Up`/`Down` registrado en orden en `GetMigrations()`
(`migrations.go`), numeración `NNN_descripción.go`, `Down` siempre implementado. Se aplican al
arrancar (`postgres.AutoMigrate`) o con `go run ./cmd/migrate` / `-rollback`. Patrón:

```go
func migration016Up(db *gorm.DB) error {
    return db.Exec(`CREATE TABLE vote_drafts (...)`).Error
}
func migration016Down(db *gorm.DB) error {
    return db.Exec(`DROP TABLE IF EXISTS vote_drafts`).Error
}
```

Numeración (invertida respecto del REQ): **023 = `relax_voting_results_vote_count`** (esta
story), 024 = `add_notifications` (S-009).

**Repositorios (convención `database`):** interfaz en `internal/storage/postgres/repository.go`,
implementación en `{entidad}_repository.go`, constructor `NewPostgres{X}Repository(db *gorm.DB)`.
IDs como `string`, firmas **sin** `context.Context`. Hoy los repositorios no reciben transacción.

### Flow Context

**avance-de-etapa-del-evento — Paso 3 (lo modifica esta story):**

Hoy:
- `PATCH /api/v1/events/{event_id}/stage`, body `{stage, estimated_end_date}`.
- Pasar a `voting` exige al menos 3 participantes registrados (`INSUFFICIENT_PARTICIPANTS`) y al
  menos 2 propuestas.
- Pasar a `results` calcula y guarda el ranking (`CalculateAndPersistResults`); si falla, la
  etapa cambia igual y el error solo se loguea.
- Operación de BD: `UPDATE events` — `stage` y `participation_estimated_end_date` o
  `voting_estimated_end_date`.

Cambio (S-006):
- Body con `voting_config` cuando `stage = voting`. Mínimo: **3 participantes con propuesta**
  (`400 INSUFFICIENT_ATTACHMENTS`, `required_minimum: 3`); se eliminan `INSUFFICIENT_PARTICIPANTS`
  y la regla de 2 propuestas. `400 MISSING_VOTING_CONFIG`, `400 INVALID_THRESHOLDS`. Etapa +
  configuración + asignaciones en una transacción; si falla → `500 VOTING_SETUP_ERROR` y el
  evento sigue en `participation`. Response con
  `voting: { configuration, assignments_count, total_attachments }`.
- `voting → results` con rankings faltantes: el resultado se persiste (CHECK relajado,
  migración 023).

Tabla de transiciones resultante:

| Transición | Precondición |
|---|---|
| `creation → participation` | `estimated_end_date` requerida |
| `participation → voting` | `estimated_end_date` + `voting_config` · **≥ 3 participantes con propuesta** |
| `voting → results` | Confirmación explícita en el diálogo (web), aun con rankings faltantes |

Paso 4 (sin cambios en esta story): emails a los participantes registrados, en segundo plano, sin
reintentos.

**configuracion-y-generacion-de-asignaciones — Pasos 1, 2 y 3:**

Hoy, `web` calcula `recommendedM = min(max(⌈2·log₂(max(k,2))⌉, 1), k−1)`, llama a
`POST …/voting-config` y luego a `POST …/generate-assignments`. Validaciones del backend antes
de escribir:

| Restricción | Significado |
|---|---|
| `m ≤ k − 1` | Nadie puede evaluar su propia propuesta |
| `m ≥ 2·log₂(k)` | Convergencia, relajada al 60% del máximo para `k ≤ 10` |
| `n · m ≥ k · min_evaluations_per_file` | Cobertura suficiente |

Algoritmo (`voting_service.go:GenerateAssignments`): fase 1, cobertura mínima con tope `m` por
participante (contador `assignmentsPerParticipant`; se saltea a quien llegó a `m`); fase 2,
completar hasta `m` excluyendo la propia. `INSERT assignments`, una fila por participante.

Cambio (S-006):

| Paso | Cambio |
|---|---|
| 1 | El `m` recomendado, mínimo y máximo los calcula **solo la api**: `GET …/voting-config/preview` |
| 2 y 3 | Ocurren dentro de `PATCH /stage` con `voting_config`, en una transacción (`UPDATE events` → `INSERT voting_configurations` → `INSERT assignments`). `POST …/voting-config` y `POST …/generate-assignments` quedan `deprecated` (con la misma regla) |
| 3 | **Evaluadores = participantes con propuesta** (`n = k`) |
| 2 | Default de `min_evaluations_per_file` = `min(3, attachments_per_evaluator)` |
| Errores | Umbrales inválidos (`good <= bad` o diferencia < 0,1) pasan de 500 (CHECK) a `400 INVALID_THRESHOLDS`, validado en Go |

**calculo-y-publicacion-de-resultados — Paso 5:** UPSERT sobre `voting_results`. Cambio: CHECK
`valid_participant_counts` relajado a `total_votes >= 0` (migración 023), así el upsert no falla

#### Description

### Task 3: `PATCH /stage` abre la votación en una sola operación

**Status:** Completed

#### Description

Reescribir la rama `participation → voting` de `UpdateEventStage`: recibir `voting_config`,

   ```go
   QualityGoodThreshold    *float64 `json:"quality_good_threshold" binding:"omitempty,min=0,max=1"`
   QualityBadThreshold     *float64 `json:"quality_bad_threshold" binding:"omitempty,min=0,max=1"`
   ```

   armado con `gin.H` (no se serializa la entidad).
