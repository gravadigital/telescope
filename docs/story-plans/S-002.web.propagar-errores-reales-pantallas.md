# Story Plan: S-002 (web) - Propagar y mostrar errores reales en pantallas de gestión y listado

## Status

**Status:** Completed

## Story Reference

- **Story:** [S-002](../stories/S-002.propagar-errores-reales-pantallas.md)
- **Service:** web
- **Summary:** Que un fallo de red o del servidor al cargar participantes, propuestas o
  estadísticas de votación se vea como error, y no como "vacío" o "no configurado", en
  `ManageEventPage` y en el modal `Participants`. Además, bloquear el avance de etapa mientras
  la lista de participantes no se haya podido verificar.

### Decisiones tomadas al planificar (aprobadas por el usuario)

1. **Se modifica `EventService.getEventParticipants`** (Tarea 1), a diferencia de lo que dice la
   story ("no se modifica"). Motivo: el servicio hace `catch { return [] }` y nunca lanza, así que
   los `try/catch` de `ManageEventPage` y `Participants` son código muerto, y CA-1, CA-4 y CA-5
   serían inalcanzables. Solo esos dos componentes llaman al método, y ambos ya envuelven la
   llamada en `try/catch`. **Pendiente:** actualizar la story S-002 y REQ-001 (sección
   Dependencias) para reflejar este cambio.
2. **Microcopy en inglés**, igual que el resto de la pantalla. El mensaje de bloqueo de la story
   ("No se puede avanzar: …") se traduce a
   `Cannot advance: the participant list could not be verified. Retry before continuing.`
3. **"Cancelar un evento" (CA-5) no aplica:** `ManageEventPage` no tiene ningún control de
   cancelación, solo de pausa (lo confirma `docs/design-system/web/components/button.md`, Deuda
   conocida #3). CA-5 se implementa sobre el avance de etapa. Pausar/reanudar no depende de los
   participantes y no se bloquea.

**Convención `error-handling` (verbatim, reglas):**

- **`setError('')` al empezar** cualquier operación, para no arrastrar el error anterior.
- **`err instanceof Error` antes de leer `.message`.** En TypeScript el `catch` es `unknown`.
- **Envolvé el mensaje del backend** en una frase con contexto. El texto crudo del backend
  suele ser técnico.
- **Toda pantalla que hace fetch necesita estado de error.** Sin él, la API falla y el
  usuario ve una pantalla vacía sin explicación.
- **No agregues manejo de 401 en los componentes**: ya está resuelto globalmente.

Patrón de referencia de la convención:

```tsx
try {
  const data = await EventService.getEventById(eventId);

  setError(`Failed to load event details: ${errorMessage}.`);
} finally {
  setLoading(false);
}
```

### Relevant ADRs

**ADR-008: Manejo global de expiración de sesión por CustomEvent**
- **Decisión:** ante un `401`, `apiRequest` limpia la sesión y emite
  `CustomEvent('auth:logout')`; `AuthContext` desloguea.
- **Implementation Rules:**
  - "**No agregues manejo de 401 en los componentes**: ya está resuelto globalmente."
  - No recargar la página ni hacer redirect duro como reacción al 401.
- **Relevancia:** los nuevos `catch` de esta story tratan cualquier error de forma genérica. No
  deben distinguir ni manejar el 401.

**ADR-006 (Create React App)** y **ADR-007 (CSS plano sin framework)**: los estilos nuevos van en
el `.css` del componente, reutilizando las clases globales existentes. No se agregan librerías.

### Design System Context — `web`

- **Versión:** v1.0.0 (`relevado-desde-código`). **Accent color de la superficie:** `#6a5acd`
  (`color.brand.primary`).
- **Grid:** desktop-first, un único corte estructural en **768px**. Los banners nuevos ocupan el
  ancho completo de su contenedor en ambos viewports, así que no necesitan reglas responsive
  propias. Si el botón `Retry` no entra al lado del texto en mobile, se permite `flex-wrap`
  dentro del media query existente de 768px.
- **Button** (`components/button.md`): no es un componente React, es un sistema de clases
  (`.btn`, `.btn-primary`, secundaria). Carga por cambio de label (`Updating...`), que es la
  solución correcta para accesibilidad → `Retry` / `Retrying...`. Deshabilitado ampliamente usado.
  ⚠️ No usar botones de solo emoji sin `aria-label`.
- **Tokens semánticos relevantes** (placeholder): `bg.error`, `text.error`, `border.error`. En
  el CSS real se expresan como `--color-danger`, `--color-danger-light` y `--color-danger-border`,
  que ya consume `.alert-danger`.
- **Accesibilidad (`guidelines/accessibility.md`, target WCAG 2.2 AA):** no comunicar estado solo
  con color (los banners llevan texto); live regions para feedback dinámico → `role="alert"` en
  cada banner de error de carga; todo control operable por teclado (botones nativos). El botón de
  avance deshabilitado se explica con el banner de error visible en la misma pantalla.
- **DS Gaps:** *Aceptados:* ninguno (REQ-001 tiene `ux_review: not-applicable`). *Nuevos:*
  ninguno. El banner de error usa la clase global `.alert-danger`, y "Alert" no está
  especificado como componente del DS, pero es la pieza ya usada en la misma pantalla (bloque
  "Alerta de error"), así que no se trata como gap.
