# Story Plan: S-016 (api) - Gestión del organizador

## Status

**Status:** Completed

## Story Reference

- **Story:** [S-016](../stories/S-016.gestion-del-organizador.md)
- **Service:** api
- **Summary:** Exponer `GET /api/v1/events/{event_id}/voting-config` (solo lectura, autor o admin)
  registrando la ruta del handler existente `DistributedVoteHandler.GetVotingConfiguration`, que
  además pasa a validar el UUID (`400 INVALID_EVENT_ID`) y a distinguir "no encontrada"
  (`404 CONFIG_NOT_FOUND`) de un error de base (`500 CONFIG_LOOKUP_ERROR`). Es la fuente de la
  "Configuración aplicada" que muestra la gestión del organizador (`web`) en Votación y Resultados.

> **Alcance de `api` en esta story: impacto bajo.** La story tiene `affects_ui: true` por `web`;
> `api` es `type: api` y no tiene pantallas, así que este plan no incluye contexto UX ni Design
> System. Sin cambios de base de datos.
>
> **Dependencias:** S-006, S-009 y S-014 están `Completed`. S-015 está `Ready`: solo aporta
> componentes de `web` y no bloquea este plan (confirmado al planificar).

### Decisiones tomadas al planificar

| # | Tema | Decisión |
|---|---|---|
| D1 | Cómo distinguir 404 de 500 | `errors.Is(err, postgres.ErrVotingConfigurationNotFound)` sobre el error de `configRepo.GetByEventID`. El centinela ya existe (`internal/storage/postgres/voting_configuration_repository.go:17`) y ya se usa igual en `voting_setup_repository.go:44`. No se crea un centinela nuevo ni se comparan strings |
| D2 | No buscar el evento en el handler | El handler **no** llama a `eventRepo.GetByID`. Para quien no es admin, `RequireEventOwner` ya respondió `404 NOT_FOUND` (forma B) si el evento no existe. Para un admin (el middleware no busca el evento) un evento inexistente responde `404 CONFIG_NOT_FOUND`, como documenta `api.yaml` |
| D3 | Mensaje del 500 | `{"error": "Failed to retrieve voting configuration", "code": "CONFIG_LOOKUP_ERROR"}`. El error real va solo al log (`h.log.Error`); nunca en el body |
| D4 | Nivel de log | No encontrada → `h.log.Debug` (es un caso esperado: la votación no se abrió). Error de base → `h.log.Error`. UUID inválido → `h.log.Warn` (como `PreviewVotingConfiguration`) |

| D7 | Documentación del servicio | Se actualiza en la Tarea 2: `docs/architectures/api/overview.md` (deuda 7), el aviso "⚠️ Hasta S-016" del Paso 4 del flujo y, si aplica, `docs/reusable-code/api/` |

**Handlers (convención `http-server`):**
- Un handler es un método sobre un struct con dependencias por constructor. Orden: 1. path params
  2. body 3. reglas de negocio 4. respuesta.
- El handler no contiene lógica de negocio: parsea, delega y responde.
- Nunca `panic` ni `uuid.MustParse` sobre entrada del usuario: `uuid.Parse` y `400` si falla.
- **Todas las rutas se registran en `cmd/api/main.go`**, en el grupo que corresponda.
- Envelope de éxito: `data`. Nunca se serializa una entidad de dominio directo: se construye el
  payload explícitamente.
- No agregar logging de entrada/salida en handlers: el middleware `events.CreateEvent()` ya lo hace.

**Grupos de rutas y autorización:**

```go
// Autenticado
events := api.Group("/events")
events.Use(auth.JWTAuthMiddleware())

// Autenticado + permiso específico
events.PATCH("/:event_id/stage",
    auth.RequireEventOwner(eventRepo),
    eventHandler.UpdateEventStage)
```

| Middleware | Permite |
|---|---|
| `RequireRole(roles...)` | Los roles globales indicados |
| `RequireEventOwner(repo)` | El autor del evento, o un `admin` |
| `RequireEventOwnerOrOrganizer(repo)` | Lo anterior, más cualquier `organizer` |
| `RequireParticipantOrOwner(repo)` | El propio participante, el autor del evento, o un `admin` |

> **Cuidado al agregar rutas.** Un endpoint declarado en `api.Group("/api/v1")` en vez de en el
> grupo que tiene `.Use(auth.JWTAuthMiddleware())` queda **público**. Verificá en qué grupo estás
> registrando.

**Reglas de `auth-jwt` al agregar endpoints:**
1. Verificá en qué grupo registrás la ruta. Fuera del grupo con `JWTAuthMiddleware()` el endpoint
   queda público.
2. Autenticado no es autorizado. Si el recurso pertenece a alguien, sumá el middleware de permiso.
3. La verificación de permisos va en el middleware, no en el handler, salvo que dependa del body.

`admin` saltea todas las verificaciones de permisos. La autoría se verifica contra
`events.author_id`, no contra el rol global.

**Comportamiento real de `RequireEventOwner`** (`internal/middleware/auth/permissions.go:49`),
forma B de error:

| Condición | Respuesta |
|---|---|
| Sin `user_id` en contexto | `401 {"error": "UNAUTHORIZED", "message": "User ID not found in context"}` |
| Sin `user_role` en contexto | `401 {"error": "UNAUTHORIZED", "message": "User role not found in context"}` |
| `user_role == admin` | `c.Next()` **sin** validar `event_id` ni buscar el evento |
| `event_id` vacío | `400 {"error": "BAD_REQUEST", "message": "Event ID is required"}` |
| `event_id` no UUID | `400 {"error": "BAD_REQUEST", "message": "Invalid event ID format"}` |
| Evento inexistente | `404 {"error": "NOT_FOUND", "message": "Event not found"}` |
| `event.AuthorID != userID` | `403 {"error": "FORBIDDEN", "message": "Only the event creator or an admin can perform this action"}` |

**Manejo de errores (convención `error-handling`), reglas para código nuevo:**
1. Usá la forma A (`{"error": "...", "code": "...", "details": "..."}`), siempre con `code`.
2. No inventes `code` nuevos si ya existe uno equivalente.
3. `details` es string.
4. No reuses un `code` entre éxito y error.
5. El status HTTP tiene que coincidir con la semántica: `401` credenciales ausentes o inválidas,
   `403` autenticado sin permiso, `404` inexistente, `409` conflicto de estado, `400` entrada
   inválida.
6. No expongas errores internos crudos. Logueá el error real y devolvé un mensaje controlado.

```go
if err != nil {
    h.log.Error("failed to create event", "error", err)
    c.JSON(http.StatusInternalServerError, gin.H{
        "error": "Failed to create event",
        "code":  "DB_CREATE_ERROR",
    })
    return
}
```

Wrapping interno con `fmt.Errorf("...: %w", err)`; inspección con `errors.Is` / `errors.As`. Para
distinguir "no encontrado", se usa un `ErrNotFound` del paquete antes que comparar strings.

**Validación de path params (convención `validation`, capa 1):**

```go
eventIDStr := c.Param("event_id")
if eventIDStr == "" {
    c.JSON(http.StatusBadRequest, gin.H{"error": "Event ID is required", "code": "MISSING_EVENT_ID"})
    return
}
eventID, err := uuid.Parse(eventIDStr)
if err != nil {
    c.JSON(http.StatusBadRequest, gin.H{"error": "Invalid event ID format", "code": "INVALID_EVENT_ID"})
    return
}
```

**Testing (convención `testing`):**
- Mocks escritos a mano en `mocks_*_test.go`, compartidos por el paquete. Al cambiar el
  comportamiento de un mock, todo el paquete lo usa: correr la suite completa.
- Tests de handler contra Gin en modo test con `httptest`, table-driven con `t.Run` cuando hay
  varios casos. `assert` para seguir, `require` cuando el resto no tendría sentido.
- **Verificá el `code` del error, no solo el status.**
- Los middlewares de `internal/middleware/auth` no tienen tests propios; la cadena se prueba
  armando un router con middleware + handler (ver `TestPreviewVotingConfiguration_OnlyTheAuthorCanSeeIt`).

### Relevant ADRs

- **ADR-004: Gin y GORM en el backend**
  - Decision: Gin 1.10.1 como framework HTTP y GORM 1.30.2 como ORM. El wiring de dependencias es
    manual y explícito en `cmd/api/main.go`, sin framework de inyección.
  - Implementation Rules: el ADR no tiene sección de reglas; aplica "`cmd/api/main.go` arma todo el
    router; `internal/storage/postgres/` contiene los repositorios".
- **ADR-005: Las entidades de dominio son a la vez modelo de persistencia y contrato JSON**
  - Decision: las structs de dominio llevan tags de GORM y JSON en el mismo campo; no hay capa de
    DTOs.
  - Aplicación acá: el contrato de este endpoint **excluye `updated_at`**, por eso el handler arma
    el payload con `gin.H` en vez de serializar `vote.VotingConfiguration` (y así lo pide también
    `http-server` para endpoints nuevos). Mantener ese payload explícito.

### API Context

#### `GET /api/v1/events/{event_id}/voting-config` (JWT + `RequireEventOwner`) — NUEVA RUTA

Copiado de `docs/apis/api.yaml`:

> Solo el autor (`RequireEventOwner`, como `GET /voting-config/preview`). Solo lectura: devuelve
> los parámetros que guardó la apertura de la votación (`PATCH /stage` con `voting_config`). La
> gestión del organizador la usa para mostrar la "Configuración aplicada" en las etapas Votación y
> Resultados; es la única fuente en Votación (`GET /distributed-results?include_metrics=true` solo
> la trae con el ranking calculado).
>
> La respuesta **no incluye `updated_at`**. Si el evento todavía no abrió la votación no hay
> configuración y responde `404 CONFIG_NOT_FOUND`.

**200:**
```json

    "id": "3f1c2d4e-5a6b-4c7d-8e9f-0a1b2c3d4e5f",
    "event_id": "9a8b7c6d-5e4f-4a3b-2c1d-0e9f8a7b6c5d",

    "quality_good_threshold": 0.6,
    "quality_bad_threshold": 0.3,
    "adjustment_magnitude": 3,
    "min_evaluations_per_file": 3,
    "created_at": "2026-10-05T13:00:00Z"
  }
}
```

| Status | Cuándo | Forma |
|---|---|---|
| `400` | `MISSING_EVENT_ID`, `INVALID_EVENT_ID` | A (`ApiError`) |
| `401` | `MiddlewareUnauthorized`: token ausente, mal formado o inválido | B (`{error: "UNAUTHORIZED", message}`) |
| `403` | `MiddlewareForbidden`: autenticado sin permiso sobre el evento | B (`{error: "FORBIDDEN", message}`) |
| `404` | `CONFIG_NOT_FOUND` — el evento todavía no abrió la votación (o, para un admin, el evento no existe: el middleware no lo busca). Para quien no es admin, un evento inexistente lo responde el middleware con `NOT_FOUND` | A |
| `500` | `CONFIG_LOOKUP_ERROR` — falla al leer la base (distinto de no encontrada) | A |

	})

func (r *PostgresVotingConfigurationRepository) GetByEventID(eventID string) (*vote.VotingConfiguration, error) {
	// "" -> errors.New("event ID cannot be empty")

	var config vote.VotingConfiguration

			return nil, ErrVotingConfigurationNotFound

	return &config, nil
}
