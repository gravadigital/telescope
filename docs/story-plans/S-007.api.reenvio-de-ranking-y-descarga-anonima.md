# Story Plan: S-007 (api) - Reenvío de ranking, descarga para evaluadores y evaluación anónima

## Status

**Status:** Completed

## Story Reference

- **Story:** [S-007](../stories/S-007.reenvio-de-ranking-y-descarga-anonima.md)
- **Service:** api
- **Summary:** Que el participante pueda reemplazar su ranking mientras dure `voting` (reemplazo
  transaccional, `replaced: true`) y guardar borradores con la asignación completa; que la
  asignación devuelva un payload explícito y **anónimo** también en `results` (con
  `404 NO_ASSIGNMENT` si no hay asignación); que el evaluador pueda descargar lo que tiene
  asignado con un nombre neutro (cierra D-15), y que el listado de propuestas con autoría quede
  solo para el organizador y el admin.

> **Fuera de alcance de este plan:** CA-11 (adaptación de `RankingVotePanel`) es del servicio
> `web` y va en su propio Story Plan. **Ver "Integration Points": el cambio de payload de la
> asignación rompe la web actual, así que `api` y `web` se despliegan juntos.**

### Decisiones tomadas al planificar (modo automático)

| # | Tema | Decisión |
|---|---|---|
| D1 | Qué se borra al reenviar y cuándo `replaced` es `true` | El envío **siempre** hace `DELETE FROM votes WHERE assignment_id = ?` + `INSERT` en una transacción, esté o no completa la asignación. `replaced = true` si el `DELETE` borró al menos una fila. Motivo: hoy el endpoint acepta envíos parciales (no exige los `m` rankings) y `votes` no tiene UNIQUE `(assignment_id, attachment_id)`; sin borrar siempre, un segundo envío tras uno parcial duplicaría votos |
| D2 | Escritura de `is_completed` / `completed_at` desde Go | Se elimina el `UpdateAssignment` que hoy hace el handler tras guardar los votos. Los mantiene solo el trigger `update_assignment_completion` (CA-2, ADR-002, flujo: "La aplicación no escribe estos campos"). El mock de repositorio simula el trigger |
| D3 | Borrador fuera de `voting` | Se elimina el `409 ASSIGNMENT_ALREADY_COMPLETED` sin agregar un chequeo de etapa: el spec (`api.yaml`) ya no lista el 409 y el borrador no afecta los votos. `VoteDraftHandler` no recibe `eventRepo` |
| D4 | Extensión del nombre neutro `propuesta-{n}.{ext}` | Mapa explícito desde los MIME que acepta la subida: `image/jpeg`→`jpg`, `image/png`→`png`, `image/gif`→`gif`, `image/webp`→`webp`, `application/pdf`→`pdf`, `text/plain`→`txt`, `application/msword`→`doc`, `application/vnd.openxmlformats-officedocument.wordprocessingml.document`→`docx`. Cualquier otro → `bin`. **Nunca** se deriva de `original_name` ni de `filename` (este último contiene el `participant_id` del autor) |
| D5 | Distinguir "sin asignación" de un error de base | Sentinela nueva `postgres.ErrAssignmentNotFound`, devuelta por `GetAssignmentByParticipant` (hoy devuelve `errors.New("assignment not found")`). Sin asignación → `404 NO_ASSIGNMENT`; otro error → `500 RETRIEVAL_ERROR` |
| D6 | Listado de propuestas sin usuario en contexto / evento inexistente | Sin `user_id` en contexto → `401 { error, code: "UNAUTHORIZED" }`. Si falla la búsqueda del evento se trata como "no es el autor": se filtran las propias, así un evento inexistente sigue respondiendo `200 data: []` como documenta el spec |
| D7 | Datos de las propuestas en la asignación | Una sola consulta `attachmentRepo.GetByEventID(eventID)` + mapa por id. Si un id de `attachment_ids` no está en el evento → `500 RETRIEVAL_ERROR` (violación de integridad; el trigger lo impide al crear). `description` vacía → `null` |
| D8 | Posición `n` de la etiqueta y del nombre neutro | Una sola función de dominio `(*Assignment).PositionOf(attachmentID uuid.UUID) (int, bool)`, 1-based sobre `attachment_ids`. La usan el `label` y la descarga, así `Propuesta 2` y `propuesta-2.pdf` siempre coinciden |
| D9 | Orden de permisos en la descarga | admin → dueño de la propuesta → autor del evento (todos con `original_name`) → evaluador con la propuesta en su asignación del mismo evento y etapa `voting`/`results` (nombre neutro) → `403`. Cualquier error al buscar evento o asignación **cierra** (403) |
| D10 | `uuid.MustParse` en `SubmitRankingVotes` | Se reemplaza por `uuid.Parse` con `400` (convención `http-server`: nunca `MustParse` sobre entrada del usuario), ya que se toca el handler |

**Handlers (convención `http-server`):**

- Un handler es un método sobre un struct que recibe sus dependencias por constructor. Orden
  interno: 1. path params 2. body 3. reglas de negocio 4. respuesta.
- El handler no contiene lógica de negocio: parsea, delega y responde.
- Nunca `panic`. Nunca `uuid.MustParse` sobre entrada del usuario: `uuid.Parse` y `400` si falla.
- **Todas las rutas se registran en `cmd/api/main.go`**. Las rutas de esta story ya existen y no
  cambian (ver API Context).
- **Nunca serializar una entidad de dominio directo**: construir el payload explícitamente
  (ADR-005 sigue vigente para el código existente, pero el código nuevo arma `gin.H`). Es
  justamente lo que hoy filtra autoría en `GET …/assignment` (`"assignment": assignment`).
- No agregar logging de entrada/salida de requests.

**Validación (convención `validation`):** 1) path params manual; 2) body con binding tags
(`INVALID_PAYLOAD` + `details`); 3) reglas de negocio manuales. Las reglas que imponen los
triggers conviene validarlas también en Go antes, porque el error del trigger llega como `500`.

**Manejo de errores (convención `error-handling`):**

- Forma A (objetivo), siempre con `code`: `{ "error": "mensaje legible", "code": "SCREAMING_SNAKE", "details": "string opcional" }`.
- Forma legacy (`LegacyError`: `{ "error": "..." }` + campos extra como `current_stage`) se
  mantiene **donde el spec la mantiene**: 400/403/404-de-evento de `…/assignment` y todos los
  errores de `…/ranking-votes`. No migrar esos errores en esta story (el spec los declara
  `LegacyError`).
- Status: `400` entrada inválida, `401` sin sesión, `403` sin permiso, `404` inexistente, `500` interno.
- No exponer errores internos crudos: loguear el real y devolver un mensaje controlado.
- Entre capas: `fmt.Errorf("...: %w", err)`; inspección con `errors.Is`. Errores centinela con
  prefijo `Err` en el paquete que los produce.

```go
if err != nil {
    h.log.Error("failed to retrieve assignment", "error", err, "event_id", eventID)
    c.JSON(http.StatusInternalServerError, gin.H{
        "error": "Failed to retrieve assignment",
        "code":  "RETRIEVAL_ERROR",
    })
    return
}
```

**Logging (convención `logging`):** pares clave-valor; logger por componente obtenido en el
constructor (`logger.Handler("attachment")`). No loguear tokens.

**Base (`_base`):** `gofumpt`; sin estado global mutable; constantes `MixedCaps`; errores
centinela `Err...`; comentarios solo para el "por qué".

### Relevant ADRs

**ADR-001: Votación distribuida por pares con Modified Borda Count**
- Decisión: cada uno de los `n` participantes recibe `m` propuestas de las `k` totales; nadie
  recibe la propia. Ranking `R_i: A(p_i) → {1..m}`, 1 = mejor.
- Aplica a esta story: el reemplazo del ranking no cambia el modelo: siguen siendo `m` votos por
  asignación. **Quien no completa su asignación recibe `Q_i = 0`**; por eso importa que, si un
  reemplazo deja la asignación incompleta, el trigger la marque `is_completed = false`.

**ADR-002: Reglas de negocio implementadas en triggers de PostgreSQL**
- Decisión: invariantes en plpgsql (`004_constraints_and_triggers.go`; funciones de validación
  recreadas en `022`).

| Regla | Mecanismo |
|---|---|
| El votante debe tener una asignación en el evento | `validate_vote_constraints` (BEFORE INSERT/UPDATE ON votes) |
| Solo se vota lo que está en la propia asignación | `validate_vote_constraints` |
| `rank_position ≤ attachments_per_evaluator` | `validate_vote_constraints` |
| Cálculo del score Borda si viene nulo | `validate_vote_constraints` |
| Marcado de asignación completa | `update_assignment_completion` (AFTER INSERT y AFTER DELETE ON votes) |
| Mantenimiento de `attachments.vote_count` | `update_attachment_vote_count` (AFTER INSERT OR DELETE ON votes) |

- **Regla a cumplir:** antes de modificar cualquier regla de asignación o votación, leer
  `internal/storage/migrations/004_constraints_and_triggers.go`. Si la regla existe en los dos
  lados, cambiar los dos en la misma story.
- Aplica a esta story: **no se toca ningún trigger.** El reemplazo se apoya en que
  `update_assignment_completion` y `update_attachment_vote_count` corren también en `DELETE`.
  Una violación de trigger dentro de la transacción hace rollback y conserva los votos previos.

**ADR-005: Las entidades de dominio son a la vez modelo de persistencia y contrato JSON**
- Decisión: structs de dominio con tags GORM y JSON, sin DTOs.
- Aplica a esta story: es la causa de la filtración en `GET …/assignment`. La respuesta pasa a
  construirse con `gin.H` explícito; `vote.Assignment` no se serializa más en ese endpoint.

### API Context

Spec ya actualizado en `docs/apis/api.yaml` (secciones citadas abajo, copiadas).

**Middlewares de las rutas involucradas (`cmd/api/main.go`, no cambian):**

| Ruta | Middleware |
|---|---|
| `GET /api/v1/events/:event_id/attachments` | Grupo `events` con `JWTAuthMiddleware` (cualquier usuario con sesión) |
| `GET /api/v1/events/:event_id/participants/:participant_id/assignment` | `RequireParticipantOrOwner(eventRepo)` |

`RequireParticipantOrOwner`: `admin` pasa; si `user_id == participant_id` pasa; si no, solo el
autor del evento (`event.AuthorID`). Errores en forma B (`{ "error": "FORBIDDEN", "message": "..." }`).
`JWTAuthMiddleware` deja en el contexto `user_id` (string uuid) y `user_role`
(`participant.Role`), que se leen con `auth.GetUserIDFromContext(c) (uuid.UUID, error)` y
`auth.GetUserRoleFromContext(c) (participant.Role, error)`.

"Organizador" en esta story = **autor del evento** (`events.author_id`). El rol global
`organizer` sin autoría del evento es un usuario más.

**`GET /api/v1/events/{event_id}/participants/{participant_id}/assignment`**

> Las propuestas que le tocó evaluar. Solo el propio participante, el autor del evento o un
> admin, en etapa `voting` o `results` (S-007). Payload construido explícitamente (S-007):
> **anónimo**, sin autor ni nombre original de cada propuesta y sin campos internos
> (`quality_score`, `expertise_match_score`, `conflict_of_interest`). Un inscripto sin
> asignación recibe `404 NO_ASSIGNMENT`.

Response 200:
```yaml
assignment:                    # AnonymousAssignment
  id: uuid
  event_id: uuid
  is_completed: boolean
  completed_at: date-time | null
  attachments:
    - id: uuid
      label: string            # "Propuesta {n}", n = posición en attachment_ids (1-based)
      mime_type: string
      file_size: integer(int64)
      description: string | null
event_name: string
participant_id: uuid           # el propio evaluador (el del path)
```
Sin envelope `data` (forma actual del endpoint, se conserva). **No** incluye `attachment_ids`,
`participant_id` de ninguna propuesta, `original_name`, `filename`, `file_path`, `vote_count`,
`quality_score`, `expertise_match_score`, `conflict_of_interest`, `assignment_round`, `votes`.

Errores:
- `400` (LegacyError): parámetros faltantes, o el evento no está en `voting` ni `results`
  (`{ "error": "Assignments are only available during voting and results stages", "current_stage": "<stage>" }`).
- `401` middleware.
- `403` (LegacyError): `{ "error": "Participant is not registered for this event" }`.
- `404`: evento inexistente (LegacyError `{ "error": "Event not found" }`); **`NO_ASSIGNMENT`**
  (forma A): `{ "error": "Participant has no assignment in this event", "code": "NO_ASSIGNMENT" }`.
- `500` (forma A): `RETRIEVAL_ERROR`.

---

**`POST /api/v1/events/{event_id}/participants/{participant_id}/ranking-votes`**

> Envío definitivo. Los rangos tienen que ser enteros consecutivos desde 1, sin duplicados, y
> cada propuesta tiene que pertenecer a la asignación del participante. **Reenvío (S-007):** si la
> asignación ya está completa y el evento sigue en `voting`, el ranking nuevo reemplaza al
> anterior (`DELETE` + `INSERT` en una transacción; los triggers mantienen `is_completed` y
> `vote_count`) y la respuesta trae `replaced: true`. Fuera de `voting` responde 400.
> Respuesta plana, sin envelope `data` ni `code`.

Request (sin cambios):
```yaml
assignment_id: uuid            # req
rankings:                      # req, minItems 1
  - attachment_id: uuid        # req
    rank: integer              # req, minimum 1, 1 = mejor
```

Response 201:
```yaml
message: "Ranking votes submitted successfully"
event_id: uuid
participant_id: uuid
votes_count: integer
replaced: boolean              # true si reemplazó un ranking anterior (S-007; ver D1)
```

Errores (todos LegacyError, se conservan los mensajes actuales):
- `400`: payload inválido (`{ "error": "Invalid request payload", "details": "..." }`), etapa
  incorrecta (`{ "error": "Voting is only allowed during voting stage", "current_stage": "<stage>" }`),
  `assignment_id` inválido o que no corresponde, rangos duplicados
  (`"Duplicate rank found"`) o no consecutivos, propuesta no asignada
  (`"Attachment is not assigned to this participant: <id>"`) o de otro evento.
- `403`: `{ "error": "Participant is not registered for this event" }`.
- `404`: evento, asignación o propuesta inexistente.
- `500`: fallo al guardar los votos.
- **Se elimina** `409 VOTES_ALREADY_SUBMITTED`.

---

**`PUT /api/v1/events/{event_id}/participants/{participant_id}/vote-draft`**

> Guardado parcial; no valida duplicados ni consecutividad. Un borrador por par (asignación,
> participante): upsert. Se acepta también con la asignación completa mientras el evento esté en
> `voting` (S-007).

Request `{ rankings: [{ attachment_id: uuid, rank: integer ≥ 1 }] }` (req). Response 200
`{ message, data: { assignment_id, participant_id, rankings_count, updated_at }, code: "DRAFT_SAVED" }`.
Errores: `400` `INVALID_EVENT_ID`, `INVALID_PARTICIPANT_ID`, `INVALID_PAYLOAD`,
`INVALID_ATTACHMENT_ID`; `401`; `404 ASSIGNMENT_NOT_FOUND`; `500 DRAFT_SAVE_ERROR`.
**Se elimina** `409 ASSIGNMENT_ALREADY_COMPLETED`.

---

**`GET /api/v1/attachments/{attachment_id}/download`**

> Pueden descargarla su dueño, el autor del evento o un `admin`, y (S-007) quien la tiene en su
> asignación del mismo evento en etapa `voting` o `results` (cierra D-15). El permiso se
> verifica en el handler (`canDownload`), no con un middleware de ruta. **Anonimato:** para el
> evaluador, `Content-Disposition` usa un nombre neutro `propuesta-{n}.{ext}` (n = posición en
> `attachment_ids`), nunca el nombre original.

Response 200: binario. Headers: `Content-Disposition: attachment; filename="<original_name>"`
(o `propuesta-{n}.{ext}` para el evaluador), `Content-Type: <mime_type>`,
`Content-Length: <file_size>`.

Errores (forma A): `401`; `403 FORBIDDEN` (`{ "error": "You are not authorized to download this attachment", "code": "FORBIDDEN" }`);
`404 ATTACHMENT_NOT_FOUND`, `FILE_NOT_FOUND`.

**`GET /api/v1/events/{event_id}/attachments`**

> No valida el formato del UUID ni la existencia del evento: un evento inexistente devuelve `200`
> con `data: []`. **Anonimato (S-007):** el autor del evento y un `admin` reciben todas las
> propuestas; cualquier otro usuario recibe solo las propias.

Response 200 (forma sin cambios):
```yaml
data:
  - id: uuid
    event_id: uuid
    participant_id: uuid
    original_name: string
    file_size: integer(int64)
    mime_type: string
    description: string        # se omite si está vacía
```

Errores: `401` (middleware; y forma A `UNAUTHORIZED` si el handler no encuentra el usuario, D6),

**`attachments`**: `id`, `event_id`, `participant_id` (autor), `filename` (nombre de storage:

**Trigger `update_assignment_completion`** (copiado de `004_constraints_and_triggers.go`), AFTER
INSERT y AFTER DELETE ON `votes`, FOR EACH ROW:
```sql
SELECT * INTO assignment_record FROM assignments
WHERE event_id = COALESCE(NEW.event_id, OLD.event_id)
  AND participant_id = COALESCE(NEW.voter_id, OLD.voter_id);
IF FOUND THEN
    expected_votes := array_length(assignment_record.attachment_ids, 1);
    SELECT COUNT(*) INTO actual_votes FROM votes
    WHERE event_id = assignment_record.event_id AND voter_id = assignment_record.participant_id;
    IF actual_votes >= expected_votes AND NOT assignment_record.is_completed THEN
        UPDATE assignments SET is_completed = TRUE, completed_at = CURRENT_TIMESTAMP WHERE id = assignment_record.id;
    ELSIF actual_votes < expected_votes AND assignment_record.is_completed THEN
        UPDATE assignments SET is_completed = FALSE, completed_at = NULL WHERE id = assignment_record.id;
    END IF;
END IF;
```
Consecuencia: durante el reemplazo, el primer `DELETE` pone `is_completed = FALSE` y
`completed_at = NULL`; los `INSERT` lo vuelven a `TRUE` con `completed_at = CURRENT_TIMESTAMP`
(= inicio de la transacción) cuando se alcanzan los `m` votos. **Ojo en los tests de
integración:** todo corre dentro de la transacción de `migratedTx`, así que `CURRENT_TIMESTAMP`
es el mismo en el primer envío y en el reemplazo; afirmar `completed_at IS NOT NULL`, no que
cambió.

**Trigger `update_attachment_vote_count`**, AFTER INSERT OR DELETE ON `votes`: `INSERT` →
`vote_count + 1` sobre `NEW.attachment_id`; `DELETE` → `vote_count - 1` sobre `OLD.attachment_id`.

**Sin migraciones en esta story.**

#### Description

   - **No** escribe `assignments` (D2).
