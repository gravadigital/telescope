# Story Plan: S-007 (web) - Reenvío de ranking, descarga para evaluadores y evaluación anónima

## Status

**Status:** Completed

## Story Reference

- **Story:** [S-007](../stories/S-007.reenvio-de-ranking-y-descarga-anonima.md)
- **Service:** web
- **Summary:** Adaptación mínima de `RankingVotePanel` al contrato anónimo que la `api` ya
  implementó en S-007. El panel toma los datos de las propuestas desde la asignación (y no del
  listado del evento, que ahora solo devuelve la propia), las muestra como "Propuesta N", las
  descarga con un nombre neutro y trata el `404 NO_ASSIGNMENT`. La pantalla nueva de ranking
  (lista ↑↓, reenvío, solo lectura en Resultados) es S-017.

### Por qué esta story rompe la web si no se adapta

La `api` de S-007 ya está en `main`/esta rama (commit `457d3a3`). Con ese cambio el panel actual
deja de funcionar:

1. `GET …/assignment` ya no trae `attachment_ids`: `assignmentData.attachment_ids.includes(...)`
   (`RankingVotePanel.tsx:61-62`) lanza `TypeError` y el panel cae en el error genérico.
2. `GET /events/{event_id}/attachments` devuelve a un participante solo **su propia** propuesta:
   aunque se arreglara (1), el filtro dejaría la lista de ranking vacía.
3. Las propuestas ya no traen `original_name` ni `uploaded_at` (regla de anonimato).
4. El link de descarga es un `<a href>` directo a `att.url` **sin token**: el backend exige
   `Authorization: Bearer`, así que nunca funcionó para el evaluador (D-15).
5. Un inscripto sin propuesta recibe `404 { error: "Participant has no assignment in this event",
   code: "NO_ASSIGNMENT" }`. El panel busca `'not found'` / `'404'` en el mensaje, no lo encuentra
   y muestra "Failed to load your assignment", y antes mostraba un "Voting has not been
   configured yet" que ya no es cierto (S-006 abre la votación con las asignaciones en un paso).

### Decisiones tomadas al planificar (modo automático)

1. **Alcance = CA-11 y lo que hace falta para que se cumpla.** CA-1 a CA-10 son de la `api`
   (Done). La web consume CA-5 (payload anónimo), CA-7 (`NO_ASSIGNMENT`), CA-8 (descarga del
   evaluador) y vive con CA-10 (listado filtrado). **No** entran: reenvío desde la UI, lista ↑↓,
   ranking en solo lectura en `results` (CA-6 del lado web) → S-017; estado "sin propuesta en
   votación" con el diseño nuevo → S-015.
2. **El panel completado se mantiene** ("Assignment Completed"), sin el puntaje de calidad
   (`quality_score` ya no viene en el payload). Reenviar desde la UI es S-017.
3. **`apiRequest` conserva `status` y `code` en el `Error` que lanza** (Tarea 1). El mensaje no
   cambia, así que ningún llamador existente se rompe. Es la forma mínima de distinguir
   `NO_ASSIGNMENT` sin buscar substrings, que la convención `error-handling` señala como frágil.
   S-010 lo formaliza en la clase `ApiError` (DA-6); esta story **no** crea esa clase para no
   adelantar su diseño.
4. **El nombre neutro del archivo se arma en la web** (`propuesta-{n}.{ext}`, mismo mapa MIME →
   extensión que la `api`). `downloadFile` usa `link.download = filename`, así que el nombre que
   ve el usuario es el que pasa la web; el `Content-Disposition` del backend no se lee (el
   header no está expuesto por CORS y `downloadFile` no lo usa).
5. **La etiqueta es `label` tal como viene de la api** ("Propuesta 1"), como pide CA-11 en forma
   literal. El resto del panel sigue en inglés. Traducirla por índice es de S-011 (i18n).
6. **Microcopy nuevo en inglés**, como el resto del panel (mismo criterio que S-002).

**Convención `project-structure` (reglas aplicables):**
- Carpeta en `kebab-case`, archivo del componente en `PascalCase`; un componente por carpeta,
  con su CSS al lado.
- **`export default`** para el componente. Los tipos y helpers van con export nombrado.
- Los tipos compartidos van en `src/types/index.ts`.
- `strict: true`: **nada de `any` en código nuevo**. `src/services/api.ts` tiene varios
  `Promise<any>` heredados: no los imites, tipá la respuesta.

**Patrón de fetching (convención `data-fetching`):** tres capas. `config/api.ts` (`apiRequest`)
→ `services/api.ts` (normaliza el envelope y devuelve tipos limpios, ADR-005) → componente

**Convención `error-handling` (verbatim, reglas):**

- **`setError('')` al empezar** cualquier operación, para no arrastrar el error anterior.
- **`err instanceof Error` antes de leer `.message`.** En TypeScript el `catch` es `unknown`.
- **Envolvé el mensaje del backend** en una frase con contexto. El texto crudo del backend
  suele ser técnico.
- **Toda pantalla que hace fetch necesita estado de error.** Sin él, la API falla y el
  usuario ve una pantalla vacía sin explicación.
- **No agregues manejo de 401 en los componentes**: ya está resuelto globalmente.

Patrón de referencia:

```tsx
try {
  const data = await EventService.getEventById(eventId);
} catch (err) {
  const errorMessage = err instanceof Error ? err.message : 'Unknown error';
  setError(`Failed to load event details: ${errorMessage}.`);
} finally {
  setLoading(false);
}
```

Fragmento de la convención que motiva la Tarea 1 (verbatim):

> **Efecto colateral importante: se pierde el `code`.** El backend manda un identificador
> estable (`EVENT_NOT_FOUND`, `MAX_PARTICIPANTS_REACHED`, …) y el cliente se queda solo con el
> texto. Por eso los componentes terminan haciendo `err.message.includes('INVALID_PAYLOAD')`
> para distinguir casos: frágil y dependiente del idioma del mensaje.
>
> **Si se mejora una sola cosa del manejo de errores, que sea preservar el `code`** — por
> ejemplo con una clase `ApiError` que lleve `code`, `message` y `status`. Habilita mensajes
> por caso sin buscar substrings.

### Relevant ADRs

**ADR-005: Las entidades de dominio son a la vez modelo de persistencia y contrato JSON**
- **Decisión:** la `api` no tiene capa de DTOs; la `web` absorbe la normalización:
  "`src/services/api.ts` normaliza las respuestas y devuelve tipos limpios a los componentes".
- **Relevancia:** `GET …/assignment` es una de las excepciones (S-007 construye el payload a
  mano para no filtrar autoría). El servicio web desenvuelve `{ assignment }` y devuelve el tipo
  limpio `AnonymousAssignment`; el componente nunca ve el envelope.

**ADR-008: Manejo global de expiración de sesión por CustomEvent**
- **Decisión:** ante un `401`, `apiRequest` limpia la sesión y emite
  `CustomEvent('auth:logout')`; `AuthContext` desloguea.
- **Implementation Rules:**
  - "**No agregues manejo de 401 en los componentes**: ya está resuelto globalmente."
  - No recargar la página ni hacer redirect duro como reacción al 401.
- **Relevancia:** la Tarea 1 toca `apiRequest`. El bloque del 401 (limpiar `localStorage` y
  emitir `auth:logout`) **se conserva idéntico**; solo cambia el objeto que se lanza después.

**ADR-006 (Create React App)** y **ADR-007 (CSS plano sin framework)**: los estilos nuevos van en
`RankingVotePanel.css` reutilizando las variables existentes. No se agregan librerías.

### Flow Context

Flujo **evaluacion-y-envio-de-ranking** (`docs/flows/evaluacion-y-envio-de-ranking.md`, ya
actualizado por la `api` de S-007). Pasos que la web toca en esta story:

**Paso 1: Consultar la asignación propia** (verbatim)
- **Método:** GET · **Endpoint:** `/api/v1/events/{event_id}/participants/{participant_id}/assignment`
- **Auth:** JWT Bearer · **Etapas:** `voting` y `results` (otra etapa → 400)
- **Response (éxito) — 200:** `AnonymousAssignment`: `assignment { id, event_id, is_completed,
  completed_at, attachments[{ id, label: "Propuesta N", mime_type, file_size, description }] }`,
  `event_name` y `participant_id`. Sin autoría, sin `original_name`, sin `attachment_ids` ni
  campos internos (`quality_score`, etc.). `N` es la posición en `attachment_ids` (1-based).
- **Response (sin asignación) — 404:** `{ error, code: "NO_ASSIGNMENT" }`.

**Paso 1b: Abrir cada propuesta asignada** (verbatim)
> El evaluador puede descargar una propuesta si la tiene en su asignación del mismo evento y el
> evento está en `voting` o `results`. El archivo se sirve con un nombre neutro
> `propuesta-{n}.{ext}` (`n` = posición en `attachment_ids`; la extensión sale del `mime_type`,
> `bin` si no está en el mapa), nunca con `original_name`. El dueño, el autor del evento y un
> `admin` reciben `original_name`. Cualquier otro caso → `403 FORBIDDEN`.
>
> `GET /api/v1/events/{event_id}/attachments` devuelve todas las propuestas solo al autor del
> evento y a un `admin`; cualquier otro usuario recibe únicamente la propia.

**Pasos 2–4** (borrador y envío): sin cambios de contrato para la web en esta story.

Tabla de errores del flujo, fila que la web implementa ahora:

| Paso | Condición | Respuesta | Qué ve el participante |
|---|---|---|---|
| 1 | Sin asignación (no participó, o no se generaron) | 404 `NO_ASSIGNMENT` | La UI no muestra el panel de ranking |
| 1b | Propuesta que no está en la asignación del evaluador, o evento fuera de `voting`/`results` | 403 `FORBIDDEN` | No puede abrirla |

"La UI no muestra el panel de ranking" se implementa como un aviso en lugar de la lista (sin
selects ni botón de envío), con el texto de la Tarea 3.

Pendiente del flujo que **no** es de esta story: lista ordenable ↑↓, solo lectura en `results`,
copy del mecanismo real (S-017); `ranking_submitted` (S-009).

### Task 1: `apiRequest` conserva `status` y `code` del error

**Status:** Completed

#### Description

`apiRequest` convierte toda respuesta no-OK en `new Error(mensaje)` y descarta el `code`. Para
reconocer `404 NO_ASSIGNMENT` sin buscar substrings en el mensaje, el `Error` lanzado pasa a
llevar `status` (HTTP) y `code` (si el body lo trae). El `message` no cambia, así que todos los
llamadores existentes siguen igual. Es el paso mínimo; S-010 lo reemplaza por la clase
`ApiError` (Decisión 3).

#### Acceptance Criteria

1. Se exporta desde `src/config/api.ts` `export interface ApiRequestError extends Error { status: number; code?: string; }`.
2. En la rama `!response.ok`, `apiRequest` lanza
   `Object.assign(new Error(errorData.error || errorData.message || \`HTTP error! status: ${response.status}\`), { status: response.status, code: typeof errorData.code === 'string' ? errorData.code : undefined })`
   (o equivalente tipado como `ApiRequestError`).
3. El bloque del 401 (limpiar `telescopio_user`/`telescopio_token` y emitir
   `CustomEvent('auth:logout', { detail: { reason: 'token_expired' } })`) queda idéntico y se
   ejecuta antes del `throw`.
4. Se exporta un helper `export const getErrorCode = (err: unknown): string | undefined` que
   devuelve `err.code` si `err instanceof Error` y `code` es string; si no, `undefined`.
5. `downloadFile` y `uploadFile` no cambian.
6. TS-1 a TS-4 pasan.

#### Technical Details

**Architectural Context References:**
