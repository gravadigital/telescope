# Story Plan: S-001 (web) - Eliminar datos fabricados de la capa de servicios (api.ts)

## Status

**Status:** Ready

## Story Reference

- **Story:** [S-001](../stories/S-001.eliminar-datos-fabricados-servicios.md)
- **Service:** web
- **Summary:** Eliminar los fallbacks de datos fabricados en la capa de servicios (`api.ts`) y el
  login demo de `AuthForm.tsx`, y conectar el health check real en `Auth.tsx`, para que ningún
  fallo de red o del servidor se disfrace de dato real, lista vacía silenciosa o sesión válida.

## Architectural Context

react-scripts 5.0.1     typescript 4.9.5

Create React App puro (`ADR-006`). Sin SSR, sin Server Components, sin file-based routing.

### Service Architecture

Organización **por tipo técnico**, no por dominio:

```
src/
├── App.tsx              # rutas, navbar, providers
├── components/{kebab-case}/
│   ├── Component.tsx
│   └── Component.css
├── pages/{kebab-case}/
├── context/             # React Context (AuthContext)
├── services/api.ts      # llamadas a la API por dominio (872 líneas)
├── config/api.ts        # URL base, endpoints, cliente fetch (apiRequest)
└── types/index.ts
```

**Patrón de manejo de errores (convención `error-handling`):** cada pantalla usa `try/catch` con
estado local. No hay error boundaries. El 401 se maneja globalmente vía `CustomEvent` (ver
ADR-008 abajo) y **no debe tocarse en los componentes**.

**Patrón de fetching (convención `data-fetching`):** tres capas —
`config/api.ts` (`apiRequest`, cliente HTTP transversal) → `services/api.ts` (traducción
API↔frontend por dominio) → componente (`loading`/`error`/dato en `useState`). Sin caché, sin
React Query/SWR.

**Testing (convención `testing`):** CRA + Testing Library ya instalados
(`@testing-library/react` 16.3.0, `@testing-library/user-event` 13.5.0). Prácticamente sin
cobertura hoy — un solo smoke test en todo el proyecto. Mockear `src/services/api.ts` con
`jest.mock`, no interceptar `fetch`. Todo lo que use `useAuth()` necesita `<AuthProvider>` (lanza
si no).

### Relevant ADRs

**ADR-008: Manejo global de expiración de sesión por CustomEvent**

- **Decisión:** Ante un `401`, `apiRequest` (`src/config/api.ts`) limpia la sesión de
  `localStorage` y emite `window.dispatchEvent(new CustomEvent('auth:logout', { detail: { reason:
  'token_expired' } }))`. `AuthContext` (`src/context/AuthContext.tsx:81-95`) escucha ese evento
  y desloguea sin recargar la página.
- **Implementation Rules (verbatim):**
  - "**No agregues manejo de 401 en los componentes**: ya está resuelto globalmente." (de
    `conventions/error-handling.md`)
  - No se debe recargar la página (`window.location.reload()`) ni hacer redirect duro como
    reacción al 401.
  - Si se toca este código: "extraer `'auth:logout'` a una constante compartida y tipar el
    evento" es la mejora recomendada, pero **no es parte del alcance de esta story** — no
    tocar `apiRequest` ni `AuthContext` más allá de lo que ya describen las tareas.
- **Relevancia para esta story:** Ninguna tarea de S-001 modifica `apiRequest` ni el manejo de
  401/`auth:logout`. Se documenta para que el implementor NO lo toque al tocar código cercano
  (`config/api.ts`, `AuthContext.tsx` están en el mismo archivo/módulo que código que sí cambia).

**`src/services/api.ts` — `EventService.getEventById` (líneas 179-230):**

```ts
async getEventById(id: string): Promise<Event | null> {
  try {
    const response = await apiRequest<{ data: any }>(`${API_CONFIG.ENDPOINTS.EVENTS}/${id}`);
    if (!response || !response.data) {
      throw new Error("No response from API");
    }
    // ... mapeo a Event (sin cambios) ...
    return { /* ... */ };
  } catch (error) {
    console.warn("⚠️ Failed to fetch event by ID from API, checking fallback data:", error);
    try {
      const allEvents = await this.getAllEvents();
      const event = allEvents.find(e => e.id === id);
      if (event) return event;
    } catch (fallbackError) {
      console.error("Fallback also failed:", fallbackError);
    }
    console.error("❌ Event not found:", id);
    return null;
  }
}
```

Debe quedar: el bloque `catch` elimina el intento de fallback vía `this.getAllEvents()` (líneas
215-225) y hace `throw error;` en vez de `return null`. **Importante:** este método ya devuelve
`null` correctamente para el caso "respuesta 200 sin `data`" — eso se mueve a una verificación
explícita del camino feliz, no cambia su semántica. Lo que cambia es exclusivamente el `catch`:
un error real de red/servidor pasa a relanzarse en vez de devolver `null` (indistinguible de "no
encontrado") o el evento fabricado.

**`src/services/api.ts` — `UserService.getUserEvents` (líneas 518-537):**

silencia errores de red/servidor reales), pero si el implementor prefiere unificar tratándolo
también como error, es una decisión de detalle sin impacto en los AC — lo que es innegociable es
que el bloque `catch` relance.

## Tasks

### Task 1: Eliminar fallbacks fabricados en `EventService` (`api.ts`)

**Status:** Completed

#### Description

`EventService.getAllEvents` y `EventService.getEventById` (`src/services/api.ts`) fabrican datos
falsos o encadenan un fallback fabricado ante un error real de red o servidor. Esta tarea elimina
ambos fallbacks para que el error real se propague al caller, que ya sabe manejarlo.

#### Acceptance Criteria

1. `EventService.getAllEvents()` relanza el error (`throw error` o equivalente) en su `catch` en
   vez de devolver el array de 2 eventos fabricados (`id: "68a94135-..."`, `id: "660e8400-..."`).
2. `EventService.getEventById(id)` relanza el error en su `catch` en vez de intentar
   `this.getAllEvents()` como fallback y devolver `null` tras agotar ese intento.
3. `EventService.getEventById(id)` sigue devolviendo `null` (sin lanzar) cuando la respuesta 200
   no trae `data` — ese comportamiento no cambia.
4. El mapeo del camino feliz de ambos métodos (construcción del objeto `Event`) no cambia.

#### Technical Details

**Architectural Context References:**
- Seguir el patrón de relanzado ya usado en `createEvent` (`api.ts:173-176`):
  `catch (error) { console.error(...); throw error; }`.
- Convención `error-handling`: la capa de servicios no fabrica datos ni silencia errores reales.
- Ver "Code to Modify" arriba para el código actual completo de ambos métodos.

**Files to Create/Modify:**
- `src/services/api.ts` (líneas 38-113 para `getAllEvents`, líneas 179-230 para `getEventById`)

**Implementation Notes:**
- No tocar el bloque de mapeo del camino feliz de ninguno de los dos métodos.
- El caller de `getEventById` (`App.tsx:84`, `EventDetailPage.tsx:70`,
  `ManageEventPage.tsx:54`) ya distingue `null` de excepción — no requieren cambios.
- El caller de `getAllEvents` (`Events.tsx:47`) ya tiene `try/catch` con `setError` — no
  requiere cambios.

**Dependencies:**
- Ninguna.

#### Testing Requirements

**Unit Tests:**
- TS-8, TS-9, TS-10 (ver Test Scenarios arriba). Mockear el módulo `../config/api`
  (`jest.mock('../config/api')`) para controlar `apiRequest`.

**Integration Tests:**
- Ninguno específico — la propagación a los componentes se cubre indirectamente porque los

### Task 2: Eliminar fallback silencioso en `UserService.getUserEvents` (`api.ts`)

**Status:** Completed

#### Description

  requiere cambios**, es una decisión aceptada explícitamente en REQ-001 (Consideraciones
  Técnicas: sincronización en background, fuera de alcance de esta story).

**Files to Create/Modify:**
- `src/services/api.ts` (líneas 518-537)
